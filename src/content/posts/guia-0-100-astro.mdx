# Guía de Astro: De 0 a 100

## ¿Qué es Astro?

Astro es un framework web moderno para construir sitios web rápidos, lanzado como versión 1.0 en 2022 y creado por **Fred Schott** (ex-Google, creador de Snowpack). Su filosofía es **content-driven**: prioriza el contenido sobre la interactividad, enviando cero JavaScript al navegador por defecto.

**Arquitectura:**
- **Zero JS by default**: Astro renderiza HTML en el servidor (build time o SSR) y elimina todo el JavaScript que no sea necesario. Tu sitio funciona sin JS.
- **Islands Architecture**: solo los componentes interactivos (islas) envían JavaScript al cliente. El resto es HTML/CSS estático.
- **MPA (Multi-Page Application)**: cada página es un HTML completo. No hay router del lado del cliente. Con ViewTransitions puedes conseguir navegación SPA-like.
- **Framework-agnóstico**: puedes usar componentes de React, Svelte, Vue, Solid, Preact, Lit, todos en el mismo proyecto.

**¿Dónde se usa?**
- **Blogs y documentación**: el caso de uso original. Sitios como el blog deAstro, docs de Netlify, y el propio docs.astro.build
- **E-commerce**: tiendas con SSR + BD, carritos interactivos con islas
- **Dashboards**: paneles de administración con server islands y componentes interactivos
- **Portfolios y landing pages**: sitios estáticos ultrarrápidos con imágenes optimizadas
- **Sitios multilingüe**: i18n routing nativo desde Astro 4
- **Headless CMS**: Astro como frontend de Contentful, Sanity, Strapi, Decap CMS

**¿Quién lo usa?** Trivius (documentación), Wayfair (e-commerce), Kontent.ai (docs), Google (varios proyectos internos), y cientos de miles de desarrolladores independientes.

Fuente: [Astro docs — Concepts](https://docs.astro.build/en/concepts/why-astro/), [Astro blog — 1.0 announcement](https://astro.build/blog/astro-1/)

### Requisitos
- **Node.js 18+** (recomendado 20 LTS o 22 LTS)
- Un editor: **VSCode** con la extensión oficial **Astro** (language server, syntax highlighting, autocompletado)

```bash
npm create astro@latest
# Sigue el asistente: nombre, plantilla (vacío, blog, portfolio, mínima), TypeScript
```



## Paradigmas

Astro es un **framework web**, no un lenguaje de programación. Sus paradigmas principales son:

### Declarativo

Los componentes `.astro` y los templates MDX siguen un estilo **declarativo**: describes *qué* renderizar, no *cómo*. El frontmatter (`---`) es imperativo (código TypeScript que se ejecuta en el servidor), pero el template es declarativo (HTML con expresiones `{}`).

```astro
---
// Imperativo: lógica en el frontmatter
const items = await getCollection('posts');
const filtrados = items.filter(p => !p.data.draft);
---
// Declarativo: template HTML con expresiones
<ul>
  {filtrados.map(item => <li>{item.data.title}</li>)}
</ul>
```

### MPA (Multi-Page Application)

Astro genera **páginas HTML completas** por cada ruta. No es una SPA: no hay router del lado del cliente. Cada navegación recarga el HTML completo (a menos que uses ViewTransitions).

| Característica | Astro (MPA) | Next.js/Nuxt (SPA/SSR) |
|---|---|---|
| HTML por ruta | Completo | Shell + JS |
| JS por defecto | Ninguno | Bundle de cliente |
| Router | Servidor (URL → archivo) | Cliente (history API) |
| ViewTransitions | SPA-like opcional | Nativo |

### Islands Architecture

Astro usa el patrón de **islas** (partial hydration): solo los componentes interactivos envían JavaScript al cliente. El resto permanece como HTML/CSS estático.

```
┌──────────────────────────────┐
│         HTML estático        │
│  ┌──────────────────────┐   │
│  │   Isla interactiva   │   │  ← solo este componente tiene JS
│  │   (React/Svelte/...) │   │
│  └──────────────────────┘   │
│         HTML estático        │
└──────────────────────────────┘
```

### Compilación estática + SSR opcional

Por defecto, Astro genera HTML estático en build time. Puedes activar SSR por página o globalmente con `output: 'server'` o `output: 'hybrid'`.

### Component-based (no POO)

Astro no usa clases ni herencia. Usa **componentes** (`.astro`, `.svelte`, `.jsx`, `.vue`) que reciben props y renderizan HTML. Es el mismo paradigma que React/Svelte/Vue, pero sin JavaScript en el cliente por defecto.

### Multi-framework

Puedes usar múltiples frameworks en el mismo proyecto:

```bash
npx astro add react svelte vue solid lit
```

```astro
---
import Mapa from '../components/Mapa.jsx';
import Contador from '../components/Contador.svelte';
import Tarjeta from '../components/Tarjeta.vue';
---

<Mapa client:only="react" />
<Contador client:load />
<Tarjeta client:visible />
```

Fuente: [Astro docs — Components](https://docs.astro.build/en/basics/astro-components/), [Astro docs — Islands](https://docs.astro.build/en/concepts/islands/)

## Tipos de datos y variables

Astro usa **TypeScript** de forma nativa. El frontmatter de los archivos `.astro` y las configuraciones de colecciones son TypeScript/JavaScript.

### TypeScript en Astro

No necesitas configurar nada: Astro incluye TypeScript por defecto. El `tsconfig.json` se genera automáticamente.

```astro
---
const nombre: string = "Astro";
const version: number = 5;
const tags: string[] = ["static", "ssr", "islands"];
const config = { output: "static" as const };
---
```

Cada componente `.astro` puede definir sus props con una interfaz TypeScript exportada:

```astro
---
export interface Props {
  name: string;
  avatar?: string;
  role: "admin" | "user" | "editor";
  joinedAt: Date;
}
const { name, avatar, role, joinedAt } = Astro.props;
---

<div class="card">
  {avatar && <img src={avatar} alt={name} />}
  <h2>{name}</h2>
  <p>{role} · {joinedAt.toLocaleDateString()}</p>
  <slot />
</div>
```

## Conceptos clave explicados a fondo

### Islas (Islands Architecture)

Las islas son componentes interactivos en medio de HTML estático. Astro renderiza el HTML en el servidor y solo hidrata (añade JavaScript) los componentes que lo necesitan, usando directivas `client:*`.

**Directivas de hidratación:**

```astro
<!-- Carga inmediata: tan pronto como la página carga en el cliente -->
<Contador client:load />

<!-- Cuando el navegador está inactivo (requestIdleCallback) -->
<MenuDesplegable client:idle />

<!-- Cuando el componente es visible en viewport (IntersectionObserver) -->
<GaleriaImagenes client:visible />

<!-- Solo en un media query específico -->
<SidebarComplejo client:media="(min-width: 768px)" />

<!-- Sin hidratación. Solo HTML y CSS -->
<BotonEstatico />

<!-- Solo cliente (no renderiza en servidor, útil para APIs del navegador) -->
<MapaInteractivo client:only="react" />
```

```astro
---
import Contador from '../components/Contador.svelte';
import Galeria from '../components/Galeria.jsx';
import Mapa from '../components/Mapa.jsx';
---

<!-- Sin JS: HTML estático -->
<Contador />

<!-- Con JS en carga -->
<Contador client:load />

<!-- Con JS cuando es visible -->
<Galeria client:visible />

<!-- Solo en cliente, sin SSR -->
<Mapa client:only="react" />
```

**¿Cómo funciona internamente?**

1. Astro renderiza el HTML de cada isla durante el build (o en SSR).
2. El HTML incluye un placeholder con atributos `data-astro-id`.
3. El runtime de Astro detecta las islas y aplica la directiva correspondiente.
4. Solo entonces se descarga y ejecuta el JavaScript del componente.

**¿Cuándo usar cada directiva?**

| Directiva | Cuándo usarla | Ejemplo |
|---|---|---|
| `client:load` | El componente debe estar disponible de inmediato | Navbar, header, banner principal |
| `client:idle` | El componente no es urgente, puede esperar | Analytics, chat widget, notificaciones |
| `client:visible` | El componente está abajo en la página | Galería de imágenes, footer interactivo, comentarios |
| `client:media` | El componente solo se ve en ciertos tamaños | Sidebar de escritorio, menú mobile |
| `client:only` | El componente usa APIs del navegador | Mapas, canvas, WebGL |

**Server Islands (Astro 4.5+)**

Desde Astro 4.5, puedes tener islas que se renderizan en el servidor en cada petición (no en build). Útil para contenido personalizado sin perder las ventajas de las islas.

```astro
---
import PrecioProducto from '../components/PrecioProducto.astro';
---

<main>
  <h1>Producto</h1>
  <!-- Esta isla se renderiza en cada request (SSR) -->
  <PrecioProducto server:defer>
    <p slot="fallback">Cargando precio...</p>
  </PrecioProducto>
</main>
```

Fuente: [Astro docs — Islands](https://docs.astro.build/en/concepts/islands/), [Astro docs — Server Islands](https://docs.astro.build/en/guides/server-islands/)

### Archivos `.astro`

Los componentes `.astro` son el corazón de Astro. Combinan HTML, CSS y JavaScript en un solo archivo.

**Estructura de un componente `.astro`:**

```astro
---
// 1. FRONTMATTER (---)
// Código JavaScript/TypeScript que se ejecuta en el servidor
// Aquí van: imports, fetch de datos, lógica, variables

import Base from '../layouts/Base.astro';
import Boton from '../components/Boton.svelte';
const titulo = "Página de ejemplo";
const datos = await fetch('https://api.example.com/data').then(r => r.json());
---

<!-- 2. TEMPLATE HTML -->
<!-- Las expresiones van entre {} -->
<Base title={titulo}>
  <main>
    <h1>{titulo}</h1>
    <ul>
      {datos.map(item => (
        <li class="item">{item.nombre}</li>
      ))}
    </ul>
    <Boton client:load />
  </main>
</Base>

<!-- 3. ESTILOS (opcional) -->
<!-- Los estilos son scoped por defecto -->
<style>
  .item {
    color: oklch(0.5 0.2 240);
  }
  h1 {
    font-size: 2rem;
  }
</style>

<!-- 4. SCRIPTS DEL LADO DEL CLIENTE (opcional) -->
<script>
  // Este código se ejecuta en el navegador
  // No confundir con el frontmatter (---) que es servidor
  document.addEventListener('DOMContentLoaded', () => {
    console.log('Página cargada');
  });
</script>
```

**Reglas importantes:**
- El frontmatter (`---`) se ejecuta en el servidor. No puedes usar `document`, `window`, `localStorage` aquí.
- El template puede contener componentes de otros frameworks, pero necesitan la directiva `client:*` para ser interactivos.
- Los estilos son **scoped por defecto**: se añade un hash único a los selectores.
- Puedes tener múltiples bloques `<style>` y `<script>`.
- `<script>` se procesa y bundlea por Vite. Si usas `is:inline`, se inserta tal cual.

**Componentes sin framework:**
```astro
---
// Card.astro — componente 100% Astro, sin framework
export interface Props {
  titulo: string;
  descripcion: string;
  imagen?: string;
}
const { titulo, descripcion, imagen } = Astro.props;
---

<article class="card">
  {imagen && <img src={imagen} alt={titulo} />}
  <h2>{titulo}</h2>
  <p>{descripcion}</p>
  <slot /> <!-- Contenido hijo -->
</article>

<style>
  .card {
    border: 1px solid oklch(0.87 0 0);
    border-radius: 0.5rem;
    padding: 1rem;
  }
</style>
```

Fuente: [Astro docs — .astro components](https://docs.astro.build/en/basics/astro-components/)

### Colecciones de contenido (Content Collections)

Las colecciones de contenido son la forma oficial de gestionar contenido en Astro. Reemplazan al patrón anterior de `Astro.glob()` para archivos Markdown/MDX.

**Configuración (`src/content/config.ts`):**
```ts
import { defineCollection, z } from 'astro:content';

const posts = defineCollection({
  type: 'content', // 'content' para MDX/Markdown, 'data' para JSON/YAML
  schema: z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.date(),
```

### SSR vs SSG, prerender, endpoints API, server islands

**SSG (Static Site Generation) — por defecto:**
```js
// astro.config.mjs
export default defineConfig({
  output: 'static', // valor por defecto
});
```
Todo se genera en build time. Los archivos HTML se sirven desde CDN. Máximo rendimiento, mínimo coste.

**SSR (Server-Side Rendering):**
```js
// astro.config.mjs
import vercel from '@astrojs/vercel/serverless';

export default defineConfig({
  output: 'server',
  adapter: vercel(),
});
```
Las páginas se renderizan en cada petición. Necesitas un adapter (Vercel, Netlify, Node).

**Hybrid / prerender (lo mejor de ambos):**
```js
// astro.config.mjs
export default defineConfig({
  output: 'hybrid', // desde Astro 3
});
```
Cada página decide si es estática o SSR:

```astro
---
// src/pages/productos/[id].astro
export const prerender = false; // Esta página usa SSR
// export const prerender = true;  // Esta página es estática

const { id } = Astro.params;
const producto = await db.getProducto(id);
---

<h1>{producto.nombre}</h1>
```

**Endpoints API:**
```astro
---
// src/pages/api/productos.json.ts
import type { APIRoute } from 'astro';

export const GET: APIRoute = async ({ params, request }) => {
  const productos = await db.findAll();
  return new Response(JSON.stringify(productos), {
    status: 200,
    headers: { 'Content-Type': 'application/json' },
  });
};

// También soporta POST, PUT, DELETE
export const POST: APIRoute = async ({ request }) => {
  const body = await request.json();
  const producto = await db.create(body);
  return new Response(JSON.stringify(producto), { status: 201 });
};
```

**Server Islands (Astro 4.5+):**
Las server islands permiten tener componentes que se renderizan en el servidor dentro de una página estática. Se cargan de forma diferida y asíncrona.

```astro
---
// Página estática con una isla de servidor
import Precio from '../components/Precio.astro';
---

<h1>Producto</h1>
<Precio server:defer>
  <p slot="fallback">Calculando precio...</p>
</Precio>
```

El componente `Precio.astro` se ejecuta en el servidor en cada petición, pero el resto de la página es estática.

Fuente: [Astro docs — SSR](https://docs.astro.build/en/guides/server-side-rendering/), [Astro docs — Server Islands](https://docs.astro.build/en/guides/server-islands/)

### ViewTransitions (navegación SPA-like)

Desde Astro 3.0, Astro incluye soporte nativo para **View Transitions**, permitiendo navegación entre páginas sin recarga completa, con animaciones fluidas.

**Configuración básica:**
```astro
---
// En tu layout principal
import { ViewTransitions } from 'astro:transitions';
---

<!doctype html>
<html>
  <head>
    <ViewTransitions />
  </head>
  <body>
    <slot />
  </body>
</html>
```

**Transiciones entre páginas:**
```astro
<!-- Página 1: /blog/post-1 -->
<a href="/blog/post-2" transition:animate="slide">Siguiente artículo</a>

<!-- Página 2: /blog/post-2 -->
<h1 transition:animate="slide">Título del artículo</h1>
```

**Animaciones disponibles:**
- `morph` — morphing del elemento entre páginas (la más espectacular)
- `slide` — deslizamiento
- `fade` — fundido
- `initial` — animación de entrada
- `only` — el elemento no se anima
- Personalizadas con `transition:name`

**Transiciones con nombres:**
```astro
<!-- Mismo nombre en ambas páginas = morphing -->
<!-- Página 1 -->
<img src="foto.jpg" transition:name="hero" />

<!-- Página 2 -->
<img src="foto-grande.jpg" transition:name="hero" />
```

**Modo de navegación:**
```astro
<ViewTransitions /> <!-- Por defecto: navegación con transiciones -->

<!-- También puedes controlar el comportamiento -->
<ViewTransitions
  client:load  <!-- Precarga los recursos de la página destino -->
/>
```

**Cuándo usarlo:**
- Blogs con navegación entre artículos
- Portfolios con galerías
- Cualquier sitio donde quieras evitar la recarga completa de página
- No lo uses en dashboards o apps con estado complejo (mejor SPA de verdad)

Fuente: [Astro docs — View Transitions](https://docs.astro.build/en/guides/view-transitions/)

### Middleware, cookies, sessions

**Middleware (Astro 3+):**
```ts
// src/middleware.ts
import { defineMiddleware } from 'astro:middleware';

export const onRequest = defineMiddleware(async (context, next) => {
  const start = Date.now();

  // Añadir datos al contexto
  context.locals.user = await getUserFromCookie(context.cookies);

  // Continuar con la petición
  const response = await next();

  // Modificar la respuesta
  const duration = Date.now() - start;
  response.headers.set('X-Response-Time', `${duration}ms`);

  return response;
});
```

```ts
// src/lib/session.ts
import { encode, decode } from 'js-cookie';

export async function getSession(cookies: AstroCookies) {
  const sessionId = cookies.get('session_id')?.value;
  if (!sessionId) return null;
  return await db.getSession(sessionId);
}

export async function createSession(cookies: AstroCookies, userId: string) {
  const session = await db.createSession(userId);
  cookies.set('session_id', session.id, {
    httpOnly: true,
    sameSite: 'lax',
    maxAge: 60 * 60 * 24 * 7, // 1 semana
    path: '/',
  });
  return session;
}
```

### Algoritmos

Astro no ejecuta algoritmos en el cliente (a menos que los programes). Todo el procesamiento ocurre en **build time** (SSG) o en **cada request** (SSR).

**Ordenación de colecciones:**
```astro
---

const porFecha = (await getCollection('posts'))
  .sort((a, b) => b.data.pubDate.valueOf() - a.data.pubDate.valueOf());

const porTitulo = (await getCollection('posts'))
  .sort((a, b) => a.data.title.localeCompare(b.data.title, 'es'));

const mix = (await getCollection('posts')).sort((a, b) => {
  const d = b.data.pubDate.valueOf() - a.data.pubDate.valueOf();
  return d !== 0 ? d : a.data.title.localeCompare(b.data.title, 'es');
});
---
```

**Agrupación (groupBy):**
```astro
---
const posts = await getCollection('posts');

const porTag = posts.reduce((acc, post) => {
  post.data.tags?.forEach(tag => {
    if (!acc[tag]) acc[tag] = [];
    acc[tag].push(post);
  });
  return acc;
}, {} as Record<string, typeof posts>);

  const anio = post.data.pubDate.getFullYear();

  return acc;
```

**Caching en build:**
En SSG los datos se cachean naturalmente: se calculan una vez en build y se incluyen en el HTML. Para SSR, usa ISR:

```js

  output: 'hybrid',
  adapter: vercel({
    isr: { expiration: 60, exclude: ['/admin/**'] },
  }),
});
```

**Tabla de complejidad algorítmica en Astro:**

| Operación | Complejidad | Contexto |
|---|---|---|
| Recorrer colección (`getCollection`) | O(n) | Build time. n = número de entradas |
| `Astro.glob()` | O(n) | Build time |
| Ordenar (sort) | O(n log n) | Build time |
| Filtrar (filter) | O(n) | Build time |
| `getEntry('posts', 'id')` | O(1) ~ O(log n) | Acceso directo por id |
| Paginación (paginate) | O(n) | Build time |
| Pagefind búsqueda en cliente | O(log n) ~ O(1) | Índice precomputado |
| Fuse.js búsqueda en cliente | O(n) | Recorre todo el índice |

En la práctica, para sitios content-driven, estas operaciones son **instantáneas** incluso con miles de entradas, porque se ejecutan en build time y no afectan al tiempo de respuesta del usuario.

### WebSocket con Node.js adapter (SSR)

```astro

// src/pages/ws.astro — página que carga el cliente WebSocket

const ws = new WebSocket('ws://localhost:3001/ws');

  const data = JSON.parse(event.data);

</script>

<div id="messages"></div>
```

```ts
// server/ws.ts — servidor WebSocket independiente
import { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 3001 });

wss.on('connection', (ws) => {
  console.log('Cliente conectado');

  ws.on('message', (data) => {
    const msg = JSON.parse(data.toString());
    // Broadcast a todos los clientes
    wss.clients.forEach(client => {
      if (client.readyState === WebSocket.OPEN) {
        client.send(JSON.stringify(msg));
      }
    });
  });

  ws.on('close', () => console.log('Cliente desconectado'));
});

console.log('WebSocket server en puerto 3001');
```

## Concurrencia

Astro maneja la concurrencia de forma diferente según el modo:

**Build (SSG):**
- Astro paraleliza la generación de páginas tanto como permite el hardware
- Las imágenes se optimizan en paralelo durante el build
- `Astro.glob()` carga archivos en paralelo
- `Promise.all()` para fetchs múltiples en el frontmatter

**SSR (Server):**
- Cada petición es independiente y concurrente
- El adapter (Vercel, Node) maneja la concurrencia de peticiones
- Puedes usar `Promise.all()` para paralelizar llamadas a BD/APIs dentro de una página

**ISR (Incremental Static Regeneration):**
- Con Vercel adapter: genera páginas bajo demanda y las cachea
- `isr: { expiration: 60 }` — la página se regenera cada 60 segundos
- Mezcla de estático y dinámico sin perder rendimiento

```astro
---
// Ejemplo: concurrencia con Promise.all en frontmatter
const [posts, usuarios, categorias] = await Promise.all([
  getCollection('posts'),
  fetch('https://api.example.com/usuarios').then(r => r.json()),
  db.query('SELECT * FROM categorias'),
]);
---
```

```js
// astro.config.mjs — ISR en Vercel
import vercel from '@astrojs/vercel/serverless';

export default defineConfig({
  output: 'hybrid',
  adapter: vercel({
    isr: {
      expiration: 60, // segundos
      exclude: ['/admin/**'], // estas páginas siempre SSR
    },
  }),
});
```

### Nivel 0–15: Fundamentos absolutos

**Qué aprender:**
- ¿Qué es Astro? Diferencia con Next.js, Nuxt, SvelteKit. Zero JS vs SPA.
- `npm create astro@latest` y estructura del proyecto
- Archivos `.astro`: frontmatter (`---`), template HTML, expresiones `{}`

- `npm run dev`, `npm run build`, `npm run preview`

## Hacks y tips de productividad

**1. Content collections con imágenes locales**
```astro
---
// Las imágenes dentro de src/ se optimizan automáticamente
import { getCollection } from 'astro:content';

const posts = await getCollection('posts');
// En el frontmatter: image: "guia_0_100_astro/guia_0_100_astro_cover-1200.webp"
// En el componente:
import { Image } from 'astro:assets';
---
{posts.map(async post => {
  const { image } = await post.data.image ? import(`../images/${post.data.image}`) : null;
  return image ? <Image src={image} alt={post.data.title} /> : null;
})}
```

**6. Deploy previews automáticos**
```yaml
# .github/workflows/deploy-preview.yml
name: Deploy Preview
on: [pull_request]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'pnpm'
      - run: pnpm install
      - run: pnpm run build
      - name: Deploy to Vercel
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          github-comment: true
```
