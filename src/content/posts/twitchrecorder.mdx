Grabar directos de Twitch manualmente es un fastidio. Siempre te pierdes el principio, o se te olvida darle a grabar, o tienes que tener OBS abierto todo el rato. La solución: un Docker que lo haga todo solo. Y no solo Twitch: también YouTube y Kick.

---

## Qué hace

TwitchRecorder detecta cuándo un canal entra en directo en Twitch, YouTube o Kick, graba el stream con calidad original (sin recompresión), y guarda el vídeo organizado por fecha. Si se pierde la conexión, reconecta automáticamente.

En resumen: arrancas el Docker y te olvidas. Cuando tu streamer favorito empiece, se graba solo.

---

## Tecnologías

- **Python** — orquestador del sistema. Controla horarios, comprobaciones, inicio/fin de grabación y organización de archivos.
- **Streamlink** — obtiene el stream de Twitch directamente. Sin navegador, sin Selenium, sin calidad reducida. Es lo que usa `vlc` por debajo.
- **yt-dlp** — obtiene el stream de YouTube y Kick. La misma herramienta que usas para descargar vídeos de YouTube.
- **Docker** — contenedor portátil. Una vez construido, funciona igual en cualquier máquina con Docker instalado.
- **FFmpeg** — dentro del contenedor, Streamlink y yt-dlp lo usan internamente para manejar el stream.

---

## Por qué no usar OBS

OBS es fantástico para grabar tu pantalla, pero para este caso de uso tiene problemas:

- Necesita tener la ventana abierta
- Consume más CPU (decodifica y vuelve a codificar)
- Si se cierra, se para la grabación
- No puedes programarlo fácilmente

Streamlink descarga el stream tal cual sale de Twitch. Sin recompresión, sin pérdida de calidad, sin CPU de más.

---

## Multi-plataforma: Twitch, YouTube y Kick

Al principio solo soportábamos Twitch con Streamlink. Pero rápidamente nos dimos cuenta de que otros streamers usaban YouTube y Kick. La solución fue usar **yt-dlp** para esas plataformas.

**¿Por qué no usar la API de YouTube?** Porque necesita una API key, tiene límites de cuota, y es más complejo de configurar. yt-dlp funciona directamente: le pasas la URL y te dice si está en directo.

El config cambia de un array simple a un diccionario con plataforma:

```json
{
    "channels": {
        "sendosama": { "platform": "twitch" },
        "MrBeast": { "platform": "youtube" },
        "adin": { "platform": "kick" }
    }
}
```

Cada plataforma usa su herramienta:

| Plataforma | Detección | Grabación |
|------------|-----------|-----------|
| Twitch | Streamlink API | Streamlink CLI |
| YouTube | yt-dlp | yt-dlp |
| Kick | yt-dlp | yt-dlp |

El `recorder.py` detecta la plataforma y ejecuta el comando correcto. Para Twitch usa Streamlink, para el resto usa yt-dlp. La lógica de monitorización, reconexión y guardado es la misma para todas.

## Archivos principales

### `config.json`

Todo se controla desde un único archivo. No hay variables de entorno complicadas ni archivos escondidos.

```json
{
    "channels": {
        "sendosama": {
            "platform": "twitch"
        },
        "MrBeast": {
            "platform": "youtube"
        },
        "adin": {
            "platform": "kick"
        }
    },
    "record_path": "/recordings",
    "days": ["Monday","Tuesday","Wednesday","Thursday","Friday","Saturday","Sunday"],
    "start_time": "21:30",
    "check_every": 30,
    "max_duration": "24:00:00",
    "retry_interval": 60,
    "copy_to_test": true
}
```

**Explicación de cada campo:**

- **`channels`** — Diccionario con los canales a grabar. Cada canal tiene un `platform` que indica de dónde viene: `twitch`, `youtube` o `kick`. Para Twitch usa Streamlink, para YouTube y Kick usa yt-dlp.

- **`record_path`** — Ruta dentro del contenedor donde se guardan los vídeos. No la cambies a menos que sepas lo que haces. El valor `/recordings` se mapea a una carpeta de tu máquina mediante `docker-compose.yml`.

- **`days`** — Días de la semana en los que se comprueba si hay directo. Si solo quieres grabar fines de semana, elimina los días entre semana.

- **`start_time`** — Hora mínima para empezar a comprobar. Si tu streamer favorito empieza a las 21:30, pon `21:30`. El Docker puede arrancar a las 17:00, pero no empezará a comprobar hasta las 21:30. Así no desperdicias recursos.

- **`check_every`** — Cada cuántos segundos se comprueba si el canal está en directo. `30` es un buen equilibrio. Si pones menos, detectas antes pero consumes más CPU.

- **`max_duration`** — Duración máxima de grabación en formato HH:MM:SS. `"24:00:00"` significa que grabará todo el directo sin límite. Si quieres limitar a 6 horas, pon `"06:00:00"`.

- **`retry_interval`** — Si se pierde la conexión pero el directo sigue activo, espera estos segundos antes de reconectar. Si el directo ya terminó (canal offline), no reintenta y para directamente.

- **`copy_to_test`** — Si es `true`, después de cada grabación copia el vídeo a una carpeta `test/` para fácil acceso. Útil en producción. Pon `false` en modo test para no llenar de copias.

### `Dockerfile`

El Dockerfile define qué hay dentro del contenedor:

```dockerfile
FROM python:3.12-slim

RUN apt-get update && \
    apt-get install -y --no-install-recommends ffmpeg && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN mkdir -p /recordings

ENTRYPOINT ["python", "-u", "main.py"]
CMD []
```

**Línea a línea:**

- `FROM python:3.12-slim` — Imagen base. Python 3.12 optimizado (sin extras innecesarios).
- `apt-get install ffmpeg` — Instala FFmpeg, que Streamlink usa internamente.
- `COPY requirements.txt .` — Copia el archivo de dependencias.
- `pip install -r requirements.txt` — Instala streamlink, requests, rich, etc.
- `COPY . .` — Copia todo el código al contenedor.
- `ENTRYPOINT ["python", "-u", "main.py"]` — Comando base. El `-u` desactiva el buffer de Python para ver los logs en tiempo real.
- `CMD []` — Argumentos vacíos por defecto. Puedes pasar `--dry-run` al ejecutar: `docker run twitchrecorder-run --dry-run`.

### `docker-compose.yml`

El docker-compose.yml define cómo ejecutar el contenedor:

```yaml
services:
  twitchrecorder:
    build: .
    container_name: twitchrecorder
    restart: unless-stopped
    volumes:
      - ./config.json:/app/config.json:ro
      - /home/jorge/test_videos:/recordings
    environment:
      - TZ=Europe/Madrid

  run:
    build: .
    volumes:
      - ./config.json:/app/config.json:ro
      - /home/jorge/test_videos:/recordings
    environment:
      - TZ=Europe/Madrid
```

**Hay dos servicios:**

1. **`twitchrecorder`** — Modo background. Siempre corriendo, se reinicia solo si se para. Ideal para dejarlo en un servidor.

2. **`run`** — Modo una vez. Ejecuta, graba y muere. Ideal para probar o para ejecutar manualmente.

**Explicación de cada opción:**

- **`build: .`** — Construye la imagen desde el Dockerfile que está en el mismo directorio.
- **`restart: unless-stopped`** — Si el contenedor se para (por error, por reinicio del PC), se arranca solo. Excepto si lo paras manualmente con `docker compose down`.
- **`volumes`** — La parte más importante:
  - `./config.json:/app/config.json:ro` — Monta tu `config.json` local dentro del contenedor. El `:ro` significa read-only: el contenedor no puede modificarlo.
  - `/home/jorge/test_videos:/recordings` — Monta una carpeta de tu máquina en `/recordings` dentro del contenedor. Los vídeos se guardan aquí.
- **`TZ=Europe/Madrid`** — Zona horaria. Importante para que los nombres de archivo tengan la hora correcta.

### `.dockerignore`

Evita que archivos innecesarios se copien al contenedor:

```
venv/
__pycache__/
.git/
recordings/
```

Esto hace que la imagen sea más ligera y que el `docker build` sea más rápido.

## Cómo funciona

```
Docker arranca
    │
    ▼
¿Hoy es día programado?
    │
    NO → Espera al siguiente día
    │
    SÍ
    ▼
¿Ya es hora de start_time?
    │
    NO → Espera (sin consumir CPU)
    │
    SÍ
    ▼
¿El canal está en directo?
    │
    NO → Espera check_every segundos
    │
    SÍ
    ▼
Inicia grabación con Streamlink
    │
    ▼
Monitor comprueba cada 5 segundos:
    │
    ├── ¿Sigue online? → Sigue grabando
    ├── ¿Se cayó pero sigue en directo? → Reconecta en retry_interval segundos
    ├── ¿El directo terminó? → Para y guarda
    └── ¿Pasó max_duration? → Para y guarda
    │
    ▼
Espera al siguiente directo
```

## Uso

### Ejecutar una vez (recomendado para probar)

```bash
docker compose run --rm run
```

- `docker compose run` — Ejecuta un servicio
- `--rm` — Elimina el contenedor al terminar (no deja basura)
- `run` — El nombre del servicio

### Dry-run (sin grabar)

```bash
docker compose run --rm run --dry-run
```

Detecta el directo pero no graba. Útil para comprobar que la config funciona sin llenar el disco.

### Ejecutar en background (para producción)

```bash
docker compose up -d
```

- `-d` — Detached mode. El contenedor corre en background.

### Ver los logs en tiempo real

```bash
docker compose logs -f
```

Los logs muestran timestamp: `17:35:28 [sendosama] Grabación iniciada`. Cuando esperas a que empiece el directo, ves cuánto falta: `Esperando 95m 30s para start_time...`. Al terminar, ves el tamaño del vídeo: `Grabación finalizada (1.2 GB)`.

### Parar todo

```bash
docker compose down
```

## Bugs encontrados durante el desarrollo

### 1. URL saltada al usar binario streamlink

En Linux, el binario `streamlink` se instala en `/usr/local/bin/streamlink`. Al usarlo directamente (en lugar de `python -m streamlink`), el código construía mal el comando y se saltaba la URL del canal:

```python
# Mal — cmd[1:] se salta la URL
cmd = ["https://www.twitch.tv/canal", "best", "-o", "archivo.mp4", "--force"]
self.process = subprocess.Popen([sl_exe] + cmd[1:], ...)

# Bien
self.process = subprocess.Popen([sl_exe] + cmd, ...)
```

### 2. Buffer de stdout lleno

Streamlink escribe mucha información a stderr (progreso, calidad, etc.). Si usas `stdout=subprocess.PIPE`, el buffer se llena y el proceso se bloquea:

```python
# Mal — el buffer se llena y el proceso muere
stdout=subprocess.PIPE, stderr=subprocess.PIPE

# Bien — redirige a /dev/null
stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL
```

## El camino recorrido: de la idea al Docker

Todo empezó con una necesidad simple: grabar directos de Twitch sin tener que estar pendiente. La idea original usaba Selenium, ChromeDriver, y automatización del navegador. Pero cuanto más lo pensábamos, más frágil parecía. Si Twitch cambiaba algo, todo se rompía.

Así que decidimos ir por otro camino: **Streamlink**. Una herramienta que hace exactamente lo que necesitamos, sin navegador, sin interfaces, sin complicaciones. Más tarde, la necesidad de grabar de YouTube y Kick nos llevó a añadir **yt-dlp**.

---

### Fase 1: Estructura y configuración

Lo primero fue definir la estructura del proyecto. Nada de un script gigante: queríamos algo limpio, separado, mantenible.

Creamos la carpeta `utils/` con módulos separados: `config.py`, `twitch.py`, `recorder.py`, `scheduler.py`, `files.py`. Cada uno con una responsabilidad clara.

El `config.py` fue el primero. La idea era tener un único `config.json` que controlara todo. Pero rápidamente nos dimos cuenta de que necesitábamos valores por defecto: si el usuario borraba un campo, el programa no podía romper. Así que `load_config()` no solo carga el JSON, también rellena lo que falte.

```python
def load_config(path: Path = CONFIG_PATH) -> dict:
    if not path.exists():
        save_config(DEFAULT_CONFIG, path)
        return DEFAULT_CONFIG.copy()

    with open(path, "r", encoding="utf-8") as f:
        config = json.load(f)

    for key, value in DEFAULT_CONFIG.items():
        if key not in config:
            config[key] = value

    return config
```

Otro detalle: detectar el sistema operativo. En Windows la ruta por defecto era `D:\Grabaciones`. En Linux no tiene sentido, así que usamos una carpeta dentro del proyecto.

```python
def _default_record_path() -> str:
    if platform.system() == "Windows":
        return "D:\\Grabaciones"
    return str(_PROJECT_DIR / "recordings")
```

### Fase 2: Detección de directos con Streamlink

Streamlink tiene una API de Python que devuelve las calidades disponibles de un canal. Lo probamos y funcionó perfecto:

```python
from streamlink import Streamlink

session = Streamlink()
streams = session.streams("https://www.twitch.tv/shinchan_oficial")
# {'160p': ..., '360p': ..., '720p': ..., 'best': ...}
```

Pero necesitábamos algo más: saber qué calidad elegir. Creamos `get_best_quality()` que busca "best" primero, y si no está, recorre una lista de calidades en orden descendente:

```python
quality_order = ["1080p60", "1080p", "720p60", "720p", "480p", "360p", "160p"]
for quality in quality_order:
    if quality in streams:
        return quality
```

Así siempre grabas a la máxima calidad posible sin complicarte.

### Fase 3: La grabación — el momento de la verdad

Llegamos al `recorder.py`, y aquí empezaron los problemas.

La idea era simple: ejecutar `streamlink URL best -o archivo.mp4` como un proceso externo. Pero había un detalle: en Windows necesitas ocultar la ventana de la consola, y en Linux no.

```python
IS_WINDOWS = platform.system() == "Windows"

popen_kwargs = dict(stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
if IS_WINDOWS:
    popen_kwargs["creationflags"] = subprocess.CREATE_NO_WINDOW
```

Pero el verdadero drama vino con el `monitor()`. Necesitábamos un hilo que comprobara cada 5 segundos si el proceso seguía vivo. Si se moría, reconectar. Si el stream terminaba, parar.

El primer intento usaba `stdout=subprocess.PIPE` para leer la salida de Streamlink. El problema: el buffer se llenaba y el proceso se bloqueaba. Streamlink escribe mucha información a stderr, y si nadie la lee, el proceso se para.

La solución fue simple pero no obvia: redirigir a `/dev/null`.

```python
# Antes — el buffer se llenaba y el proceso moría
stdout=subprocess.PIPE, stderr=subprocess.PIPE

# Después — sin buffer, sin problemas
stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL
```

Luego vino el bug de la URL. Cuando ejecutamos el contenedor en Linux, el binario `streamlink` se instalaba en `/usr/local/bin/streamlink`. El código lo encontraba bien, pero al construir el comando, se saltaba la URL:

```python
# Bug — cmd[1:] se salta la URL
cmd = ["https://www.twitch.tv/canal", "best", "-o", "archivo.mp4", "--force"]
self.process = subprocess.Popen([sl_exe] + cmd[1:], ...)  # ← URL perdida

# Corregido
self.process = subprocess.Popen([sl_exe] + cmd, ...)
```

Un simple `[1:]` que costó un buen rato de debugging.

### Fase 4: El scheduler — cuándo grabar

El `scheduler.py` es el cerebro del sistema. Decide cuándo empezar a comprobar, cuándo parar, y cómo manejar múltiples canales.

La parte más sencilla fue la comprobación de días y horas:

```python
def is_scheduled_day(config: dict) -> bool:
    today = datetime.now().strftime("%A")
    return today in config.get("days", [])

def is_after_start_time(config: dict) -> bool:
    now = datetime.now().strftime("%H:%M")
    return now >= config.get("start_time", "19:55")
```

Lo interesante es el bucle principal. Para cada canal, crea un `Recorder`. Cuando detecta un directo, lanza el recorder y un hilo de monitorización. El monitor corre en background, sin bloquear el bucle principal.

```python
if is_live(channel):
    if recorder.start():
        monitor_thread = threading.Thread(
            target=recorder.monitor,
            daemon=True
        )
        monitor_thread.start()
```

El `daemon=True` es importante: si el programa principal muere, los hilos mueren con él. No queremos hilos huérfanos corriendo en segundo plano.

filename = f"{channel}_{now.strftime('%Y-%m-%d_%H-%M-%S')}.mp4"

**`twitchrecorder`** es para producción: siempre corriendo, se reinicia solo. **`run`** es para probar: ejecuta una vez y muere.

### Fase 7: Multi-plataforma con yt-dlp

Cuando el sistema funcionaba para Twitch, preguntamos: ¿se puede hacer lo mismo para YouTube y Kick? La respuesta fue sí, pero con una herramienta diferente.

**Streamlink** funciona genial para Twitch, pero no soporta YouTube ni Kick. **yt-dlp** sí soporta las tres plataformas. La estrategia fue: usar Streamlink para Twitch (que ya funcionaba) y yt-dlp para el resto.

Lo primero fue la detección. Para YouTube:

```python
import yt_dlp

def is_live(channel: str) -> bool:
    url = f"https://www.youtube.com/@{channel}/live"
    ydl_opts = {"quiet": True, "skip_download": True}
    with yt_dlp.YoutubeDL(ydl_opts) as ydl:
        info = ydl.extract_info(url, download=False)
        return info and info.get("is_live", False)
```

Para Kick es igual pero con otra URL:

```python
def is_live(channel: str) -> bool:
    url = f"https://kick.com/{channel}"
    # Misma lógica que YouTube
```

Luego vino la grabación. yt-dlp tiene un comando similar a streamlink:

```bash
# Streamlink (Twitch)
streamlink https://www.twitch.tv/canal best -o archivo.mp4

# yt-dlp (YouTube/Kick)
yt-dlp https://youtube.com/@canal/live -f best -o archivo.mp4
```

El `recorder.py` se adaptó para detectar la plataforma y ejecutar el comando correcto:

```python
def start(self) -> bool:
    if self.platform == "twitch":
        self._start_streamlink(output_path)
    else:
        self._start_ytdlp(output_path)
```

Y el config cambió de un array a un diccionario:

```json
{
    "channels": {
        "sendosama": { "platform": "twitch" },
        "MrBeast": { "platform": "youtube" },
        "adin": { "platform": "kick" }
    }
}
```

El scheduler usa `get_channels_with_platform()` que devuelve tuplas `(canal, plataforma)`. Así sabe qué herramienta usar para cada uno.

### Fase 8: Las mejoras finales

Una vez que el sistema funcionaba, llegaron las mejoras que aparecieron con el uso real.

#### Recarga dinámica del config

El scheduler recarga `config.json` en cada ciclo. Si añades un canal mientras corre, se detecta automáticamente:

```python
config = load_config()  # Recarga en cada ciclo
```

#### Nuevo día, nuevo reset

Cuando cambia el día, los grabadores se reinician. Si un streamer estuvo offline ayer, hoy vuelve a comprobarse:

```python
today = datetime.now().strftime("%Y-%m-%d")
if today != last_day:
    for r in recorders.values():
        r.finished = False
    last_day = today
```

#### Retry interval configurable

Si se pierde la conexión pero el directo sigue activo, espera `retry_interval` segundos antes de reconectar. Si el directo terminó, para directamente:

```python
if not recorder.is_live and not recorder.finished:
    log.info(f"Reconectando en {retry_interval}s...")
    time.sleep(retry_interval)
```

#### copy_to_test

En producción, copia cada vídeo a una carpeta `test/` para fácil acceso. Se controla desde el config:

```python
if config.get("copy_to_test", False):
    test_path = base_dir / "test" / filename
    shutil.copy2(output_path, test_path)
```

#### is_after_start_time arreglado

Comparaba strings (`"9:00" >= "19:55"` fallaba). Ahora parsea horas y minutos correctamente:

```python
def is_after_start_time(config: dict) -> bool:
    now = datetime.now()
    start = config.get("start_time", "19:55")
    h, m = map(int, start.split(":"))
    return now.hour > h or (now.hour == h and now.minute >= m)
```

#### Log con timestamp

Cada mensaje incluye hora y canal. Mucho más fácil de leer que logs sin fecha:

```python
import logging

class ChannelFilter(logging.Filter):
    def __init__(self, channel=""):
        super().__init__()
        self.channel = channel

    def filter(self, record):
        record.channel = self.channel
        return True

log = logging.getLogger("twitchrecorder")
handler = logging.StreamHandler()
handler.setFormatter(logging.Formatter("%(asctime)s [%(channel)s] %(message)s", datefmt="%H:%M:%S"))
```

Resultado: `17:35:28 [sendosama] Grabación iniciada`

#### Countdown en espera

Cuando esperas a que empiece el directo, ves cuánto falta. En vez de un print cada 60 segundos, calculamos el tiempo restante:

```python
while not is_after_start_time(config):
    now = datetime.now()
    start_h, start_m = map(int, config["start_time"].split(":"))
    target = now.replace(hour=start_h, minute=start_m, second=0)
    if target < now:
        target += timedelta(days=1)
    remaining = target - now
    minutes = int(remaining.total_seconds() // 60)
    seconds = int(remaining.total_seconds() % 60)
    log.info(f"Esperando {minutes}m {seconds:02d}s para start_time...")
    time.sleep(min(60, remaining.total_seconds()))
```

Resultado: `Esperando 95m 30s para start_time...`

#### Tamaño del vídeo

Al terminar la grabación, ves cuánto pesa el archivo. Usamos `os.path.getsize()`:

```python
size_mb = os.path.getsize(output_path) / (1024 * 1024)
if size_mb > 1024:
    log.info(f"Grabación finalizada ({size_mb / 1024:.1f} GB)")
else:
    log.info(f"Grabación finalizada ({size_mb:.0f} MB)")
```

Resultado: `Grabación finalizada (1.2 GB)`

#### Modo dry-run

El último paso fue añadir `--dry-run`. Detecta el directo pero no graba. Útil para probar la config sin llenar el disco:

```python
parser = argparse.ArgumentParser()
parser.add_argument("--dry-run", action="store_true")
args = parser.parse_args()

if args.dry_run:
    log.info("=== MODO DRY-RUN (sin grabar) ===")
```

En el recorder, si `dry_run` es True, solo dice dónde grabaría:

```python
if self.dry_run:
    log.info(f"DRY-RUN: grabaría aquí")
    return False
```

### Lo que aprendimos

1. **Streamlink es fantástico** para Twitch. Sin navegador, sin dependencias, sin complicaciones.
2. **yt-dlp es la navaja suiza** para YouTube y Kick. La misma herramienta para detectar y grabar.
3. **Los buffers de subprocess** son una fuente infinita de bugs. Siempre usar `DEVNULL` a menos que necesites leer la salida.
4. **Docker facilita todo**. Una vez que funciona local, encapsularlo es trivial.
5. **Los hilos (`threading`)** son necesarios para monitorear sin bloquear. Pero hay que acordarse del `daemon=True`.
6. **Un config.json bien pensado** ahorra mucho trabajo. Los valores por defecto y la validación son esenciales.
7. **La abstracción de plataforma** permite añadir nuevas fuentes sin tocar la lógica de grabación.

## Recuperación automática

El recorder maneja varios escenarios de error:

| Escenario | Qué hace |
|-----------|----------|
| Stream pierde conexión | Espera y reconecta |
| Streamlink/yt-dlp devuelve error | Reintenta en 60 segundos |
| PC pierde Internet | Espera y continúa |
| Directo termina | Guarda el archivo y espera al siguiente |
