# Guía de Docker: De 0 a 100

## ¿Qué es Docker?

Docker es una plataforma de contenerización que permite empaquetar aplicaciones con todas sus dependencias en **contenedores** ligeros y portables. Fue lanzado por Docker Inc. (entonces dotCloud) en 2013, obra de Solomon Hykes, y revolucionó la forma en que desplegamos software.

**¿Qué lo hace diferente de una máquina virtual?**

| Aspecto | Contenedor Docker | Máquina Virtual |
|---|---|---|
| Kernel | Comparte el kernel del host | Kernel propio (huésped) |
| Arranque | Milisegundos | Minutos |
| Aislamiento | Namespaces + cgroups (nivel proceso) | Hypervisor (nivel hardware) |
| Tamaño | MB (solo app + librerías) | GB (SO completo) |
| Overhead | ~0% CPU/RAM | 5–15% CPU/RAM |
| Migración | Trivial (imagen portable) | Compleja (snapshots grandes) |

Los contenedores usan **namespaces** (pid, net, mnt, uts, ipc, user) para aislar procesos y **cgroups** para limitar recursos (CPU, RAM, disco). Esto es posible porque todos los contenedores sobre una misma máquina comparten el **kernel del host**, a diferencia de las VMs que virtualizan hardware completo.

**¿Dónde se usa Docker?**
- **Desarrollo**: entornos idénticos en local para todo el equipo, eliminando el "en mi máquina funciona"
- **CI/CD**: builds y tests reproducibles en pipelines (GitHub Actions, GitLab CI, Jenkins)
- **Producción**: despliegues escalables con Swarm o Kubernetes, microservicios, serverless
- **Edge/IoT**: contenedores ligeros en dispositivos con recursos limitados
- **Data Science**: notebooks, modelos ML, pipelines reproducibles
- **Monolíticos a microservicios**: dockerizar una app existente y partirla gradualmente

**¿Quién lo usa?** Google (todo corre en contenedores), Netflix (orquestación masiva), Spotify (microservicios en K8s), Uber (cientos de servicios), Airbnb (infraestructura con Docker + K8s).

Fuente: [Docker — What is a Container?](https://www.docker.com/resources/what-container/), [Docker Overview docs.docker.com](https://docs.docker.com/get-started/overview/), [Containers vs VMs (IBM)](https://www.ibm.com/cloud/blog/containers-vs-vms)

## ¿Cómo empezar? Instalación en todos los entornos

### Windows
1. Activa **WSL2** (Windows Subsystem for Linux): `wsl --install` en PowerShell como administrador
2. Descarga [Docker Desktop](https://www.docker.com/products/docker-desktop/) — incluye Docker Engine, CLI, Compose, BuildKit y UI
3. Durante la instalación, marca "Use WSL 2 instead of Hyper-V"
4. Verifica: abre terminal (`cmd`, PowerShell o WSL) y ejecuta `docker --version`
5. Alternativa ligera: **Docker Engine en WSL2** sin Docker Desktop (instala `docker.io` dentro de tu distro WSL)

### macOS
- **Docker Desktop** (recomendado): descarga de [docker.com](https://www.docker.com/products/docker-desktop/), incluye todo
- **Colima** (alternativa open-source): `brew install colima && colima start` — solo el Engine, sin GUI
- **OrbStack** (alternativa rápida): `brew install orbstack` — nativa Apple Silicon, más rápida que Docker Desktop
- Verifica: `docker --version && docker compose version`

### Linux (Debian/Ubuntu)
```bash
# Eliminar paquetes antiguos si existen
sudo apt remove docker docker-engine docker.io containerd runc

# Dependencias
sudo apt update
sudo apt install ca-certificates curl gnupg

# Añadir repositorio oficial Docker
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Instalar Docker Engine + Compose
sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Añadir usuario al grupo docker (evitar sudo)
sudo usermod -aG docker $USER
newgrp docker  # o cierra sesión y vuelve a entrar

# Verificar
docker run hello-world
```

Para Fedora/RHEL:
```bash
sudo dnf -y install dnf-plugin
sudo dnf config-manager --add-repo https://download.docker.com/linux/fedora/docker-ce.repo
sudo dnf install docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
```

### Docker Engine vs Docker Desktop

| Aspecto | Docker Engine | Docker Desktop |
|---|---|---|
| Componentes | Engine + CLI + Containerd + BuildKit | Engine + CLI + UI + Compose + BuildKit + Extensions |
| Plataforma | Linux | Windows, macOS (Linux vía VM) |
| Licencia | Apache 2.0 | Free para pequeñas empresas, pago para grandes |
| Consumo RAM | ~50–100 MB | ~1–2 GB (la VM come recursos) |
| Instalación | Repositorio oficial / apt / dnf | Installer con GUI |
| Ideal para | Servidores, CI/CD, producción | Desarrollo local en Win/Mac |

### Rootless mode (Linux)

Ejecuta el daemon Docker sin privilegios de root para mayor seguridad:

```bash
# Instalar dependencias del modo rootless
sudo apt install -y uidmap dbus-user-system

# Instalar rootless (después de tener docker instalado)
dockerd-rootless-setuptool.sh install

# Variables de entorno (añadir a ~/.bashrc)
export PATH=/usr/bin:$PATH
export DOCKER_HOST=unix:///run/user/$UID/docker.sock

# systemd --user
systemctl --user enable docker --now
```

Con rootless, los contenedores se ejecutan con el UID del usuario. No necesitas `sudo` ni estar en el grupo `docker`. Limitaciones: ciertas configuraciones de red (bridge por defecto solo funciona con `slirp4netns`) y monturas `--privileged` no disponibles.

## Primeros pasos y configuración del entorno

### El primer contenedor ("Hola Mundo")

```bash
docker run hello-world
```

Este comando: (1) Docker busca la imagen `hello-world` localmente; (2) no la encuentra, la descarga de Docker Hub; (3) crea un contenedor a partir de la imagen; (4) ejecuta el binario `hello` que imprime el mensaje de bienvenida; (5) el contenedor se detiene (exit 0). Has ejecutado tu primer contenedor.

### Dockerfile básico

Un Dockerfile es un script de instrucciones para construir una imagen. Cada instrucción crea una **capa** (layer) que se cachea.

```dockerfile
# app/Dockerfile
FROM node:20-alpine        # Imagen base: Node 20 sobre Alpine Linux (~120 MB)
WORKDIR /app               # Directorio de trabajo dentro del contenedor
COPY package*.json ./      # Copia solo los archivos de dependencias (capa 1)
RUN npm ci --omit=dev      # Instala dependencias de producción (capa 2)
COPY . .                   # Copia el código fuente (capa 3)
EXPOSE 3000                # Documenta el puerto (no lo abre)
CMD ["node", "server.js"]  # Comando por defecto al arrancar el contenedor
```

Construye y ejecuta:

```bash
docker build -t mi-app .       # Construye la imagen (-t = tag)
docker run -p 3000:3000 mi-app # Ejecuta: mapea puerto 3000 host → 3000 contenedor
```

### .dockerignore

Excluye archivos del contexto de build para acelerar y evitar leaks de secretos:

```dockerignore
node_modules
.git
.env
*.md
.gitignore
Dockerfile
.dockerignore
dist
.cache
npm-debug.log
```

### docker compose

Define múltiples servicios en YAML y los levanta con un solo comando:

```yaml
# compose.yml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    volumes:
      - .:/app          # bind mount para hot reload
      - /app/node_modules # anula el mount de node_modules (usa el del contenedor)
    environment:
      - NODE_ENV=development
    depends_on:
      - db

  db:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: devpassword
      POSTGRES_DB: miapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
```

```bash
docker compose up -d      # Levanta todo en background
docker compose logs -f    # Logs en vivo
docker compose exec web sh # Terminal interactiva dentro del contenedor web
docker compose down -v    # Baja todo y elimina volúmenes
```

Fuente: [Dockerfile reference](https://docs.docker.com/engine/reference/builder/), [Compose specification](https://docs.docker.com/compose/compose-file/)

## Paradigmas en Docker

Docker no es un lenguaje de programación, pero tiene una filosofía y paradigmas propios que definen cómo se construye y despliega software.

### Declarativo (no imperativo)

En el enfoque **imperativo** escribes *cómo* hacer algo paso a paso. En Docker escribes *qué* quieres — el estado deseado.

**Imperativo** (scripts de shell para configurar un servidor):
```bash
# Script imperativo: paso a paso
apt update
apt install -y nginx
echo '<h1>Hola</h1>' > /var/www/html/index.html
systemctl enable nginx
systemctl start nginx
```

**Declarativo** (Dockerfile — describes el estado final):
```dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/
# Docker se encarga de construir y ejecutar esto
```

Un `compose.yml` también es declarativo: describes servicios, redes y volúmenes, y Docker los materializa. No dices 'crea una red, luego crea un contenedor, luego conéctalo'. Dices 'quiero un servicio web con esta imagen, conectado a esta red'.

### Inmutabilidad

Las imágenes Docker son **inmutables**: una vez construidas, no cambian. Si necesitas una modificación, construyes una imagen nueva. Esto garantiza:

- **Reproducibilidad**: la misma imagen produce el mismo comportamiento siempre
- **Versionado**: cada imagen tiene un digest (SHA256) único
- **Rollbacks**: volver a una versión anterior es tan simple como desplegar la imagen anterior
- **Seguridad**: si una imagen está comprometida, construyes una nueva, no parcheas la existente

```bash
docker pull nginx:alpine
docker inspect nginx:alpine --format='{{.RepoDigests}}'
# [nginx@sha256:...] — digest único e inmutable
```

### Composición

Docker Compose implementa **composición sobre herencia**: en lugar de tener una imagen monolítica que hace de todo, compones servicios pequeños y especializados:

```yaml
services:
  api:      # Hace una cosa bien
  db:       # Hace otra cosa bien
  cache:    # Hace otra cosa bien
  worker:   # Hace otra cosa bien
```

Cada servicio es independiente, intercambiable y escalable por separado. Esto es **composición**: un todo (la app) formado por partes (servicios) que pueden reemplazarse individualmente.

### Infraestructura como Código (IaC)

Docker es una herramienta fundamental de IaC. Tu infraestructura se define en archivos (Dockerfile, compose.yml) que:

- Se versionan en Git
- Se revisan en pull requests
- Se prueban en CI/CD
- Se despliegan automáticamente

```bash
# La infraestructura vive en el repositorio
git log --oneline docker/Dockerfile
git diff docker/compose.yml
```

**Contraste con el enfoque tradicional:**
| Aspecto | Tradicional (shell) | Docker (IaC) |
|---|---|---|
| Configuración | Scripts manuales | Dockerfile + compose.yml |
| Consistencia | Depende del operador | Garantizada por la imagen |
| Versionado | No versionado | Git + tags semánticos |
| Reproducibilidad | Frágil | Garantizada (imagen inmutable) |
| Rollback | Complejo | `docker pull imagen:anterior` |

Fuente: [Infrastructure as Code (Martin Fowler)](https://martinfowler.com/bliki/InfrastructureAsCode.html), [Docker overview](https://docs.docker.com/get-started/overview/)

## Tipos de datos y variables

Docker no tiene variables en el sentido de un lenguaje de programación, pero tiene mecanismos equivalentes para parametrizar builds y ejecuciones.

### ARG vs ENV (build-time vs runtime)

| Directiva | Ámbito | Persiste en imagen | Se sobreescribe |
|---|---|---|---|
| `ARG` | Solo durante el build | No (a menos que se asigne a ENV) | `--build-arg` |
| `ENV` | Build + runtime | Sí | `-e` en docker run |

```dockerfile
# ARG — solo existe mientras se construye
ARG VERSION=latest
ARG BUILD_NUMBER
RUN echo "Versión: $VERSION, Build: $BUILD_NUMBER"

# ENV — disponible en el contenedor en ejecución
ENV NODE_ENV=production
ENV DATABASE_URL=postgres://localhost:5432/db

# ARG -> ENV (persistir un ARG en runtime)
ARG VERSION
ENV APP_VERSION=$VERSION
```

```bash
# Pasar ARG en build
docker build --build-arg VERSION=1.2.3 --build-arg BUILD_NUMBER=42 -t mi-app .

# Pasar ENV en runtime
docker run -e NODE_ENV=development -e DATABASE_URL=... mi-app
```

### Variables en docker-compose y .env

Compose interpola variables del entorno y del archivo `.env`:

```yaml
# compose.yml
services:
  web:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    ports:
      - "${PORT:-3000}:3000"
    environment:
      - DATABASE_URL=postgres://${DB_USER}:${DB_PASS}@db:5432/miapp
```

```bash
# .env (automáticamente leído por compose)
TAG=1.0.0
PORT=8080
DB_USER=admin
DB_PASS=secreto
```

Reglas de interpolación en YAML:
- `${VAR}` — usa el valor de VAR, error si no está definida
- `${VAR:-default}` — usa 'default' si VAR no está definida
- `${VAR:?error}` — error personalizado si VAR no está definida

### Tipos en YAML

Compose usa YAML, que tiene estos tipos:

```yaml
# Strings (con o sin comillas)
nombre: mi-app
version: '1.0'
descripcion: sin comillas también funciona

# Numbers
puerto: 3000
replicas: 3
limite_cpu: 0.5

# Booleans
activo: true
ssl: false
produccion: yes

# Lists
ports:
  - "3000:3000"
  - "443:443"

# Maps (diccionarios)
labels:
  app: mi-app
  env: production

# YAML Anchors & Aliases (reutilizar bloques)
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  web:
    logging: *default-logging
  worker:
    logging: *default-logging
```

### JSON, exec form y shell form

Docker distingue dos formas de escribir comandos:

```dockerfile
# EXEC FORM (JSON array) — PREFERIDA
# No invoca shell, recibe señales directamente
CMD ["python", "app.py"]
ENTRYPOINT ["docker-entrypoint.sh"]
RUN ["apt", "install", "-y", "nginx"]

# SHELL FORM (string) — invoca /bin/sh -c
# El shell procesa variables, pero no reenvía señales correctamente
CMD python app.py
ENTRYPOINT docker-entrypoint.sh
RUN apt install -y nginx
```

| Forma | Shell | Variables | Señales (SIGTERM) | Uso |
|---|---|---|---|---|
| Exec | No | No expande | Pasan al proceso directo | Preferida para CMD/ENTRYPOINT |
| Shell | Sí | Expande | Las recibe el shell | Útil para RUN con pipes |

### Tipos de imágenes

Docker ofrece variantes de imágenes base para diferentes necesidades:

| Tipo | Base | Tamaño | Caso de uso |
|---|---|---|---|
| **Full** | SO completo | ~1-3 GB | Compatibilidad máxima |
| **Slim** | SO mínimo | ~100-300 MB | Balance tamaño/funcionalidad |
| **Alpine** | Alpine Linux (musl libc) | ~5-50 MB | Imágenes mínimas, seguridad |
| **Distroless** | Solo app + runtime | ~20-100 MB | Máxima seguridad (sin shell) |
| **Scratch** | Imagen vacía | ~0-10 MB | Binarios estáticos (Go, Rust) |

```dockerfile
# Alpine: pequeña, rápida, segura
FROM node:20-alpine

# Slim: Debian mínimo, compatible con glibc
FROM python:3.12-slim

# Distroless: sin shell, sin apt, solo runtime
FROM gcr.io/distroless/java21-debian12

# Scratch: puro binario estático
FROM scratch
COPY --from=builder /bin/app /app
CMD ["/app"]
```

Alpine usa `musl libc` en lugar de `glibc`. Es más pequeña pero puede causar problemas con extensiones nativas. Distroless es la opción más segura: no tiene shell, ni `apt`, ni utilidades — solo tu app y sus dependencias.

Fuente: [Dockerfile reference — ARG](https://docs.docker.com/engine/reference/builder/#arg), [Dockerfile reference — ENV](https://docs.docker.com/engine/reference/builder/#env), [Compose variable substitution](https://docs.docker.com/compose/compose-file/#variable-substitution), [Alpine Linux](https://alpinelinux.org/), [Distroless images (Google)](https://github.com/GoogleContainerTools/distroless), [Scratch image](https://hub.docker.com/_/scratch)

## Control de flujo y modularidad

Docker no tiene estructuras de control de programación (if, for, while), pero tiene su propio flujo de construcción y ejecución basado en instrucciones del Dockerfile, multi-stage builds, BuildKit, y docker-compose.

### Instrucciones del Dockerfile como sentencias

Cada instrucción en un Dockerfile es una sentencia que modifica el sistema de archivos o la configuración de la imagen:

```dockerfile
# COPY con --chown: copia y cambia propietario en un solo paso
COPY --chown=appuser:appgroup . /app

# RUN: ejecuta comandos en una nueva capa
RUN apt update && apt install -y curl && rm -rf /var/lib/apt/lists/*

# WORKDIR: establece el directorio de trabajo (mkdir -p si no existe)
WORKDIR /app/src

# USER: cambia de usuario para siguientes instrucciones
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# EXPOSE: documenta puertos (solo documentación)
EXPOSE 3000
```

**Orden importa:** las instrucciones se ejecutan secuencialmente. El orden óptimo es de lo que menos cambia a lo que más cambia para maximizar el cache.

### Multi-stage builds (modularidad entre etapas)

Los multi-stage builds son el equivalente a funciones o módulos: cada etapa produce un artefacto, y puedes copiar selectivamente entre etapas:

```dockerfile
# Etapa 1: compilación
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app .

# Etapa 2: pruebas (opcional, solo si se necesita)
FROM builder AS tester
RUN go test ./...

# Etapa 3: imagen final mínima
FROM scratch
COPY --from=builder /app /app
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
EXPOSE 8080
ENTRYPOINT ["/app"]
```

```bash
# Construir hasta una etapa específica
docker build --target builder -t mi-app:builder .
docker build --target tester -t mi-app:tester .

# Solo construir la etapa final
docker build -t mi-app .
```

### BuildKit: monturas y heredocs

BuildKit (activado por defecto desde Docker 23.0) añade capacidades avanzadas de modularidad:

```dockerfile
# syntax=docker/dockerfile:1

FROM python:3.12-slim

# Cache persistente entre builds (no se pierde al hacer docker build)
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# Montar bind de directorio del host (sin COPY)
RUN --mount=type=bind,source=./scripts,target=/scripts \
    /scripts/setup.sh

# Heredocs (Dockerfile con sintaxis heredoc, >= Dockerfile 1.4)
RUN <<EOF
apt update
apt install -y curl git
rm -rf /var/lib/apt/lists/*
EOF
```

```bash
# Activar BuildKit explícitamente
DOCKER_BUILDKIT=1 docker build .
```

### docker-compose: profiles, depends_on, healthcheck

Compose ofrece control de flujo para entornos modulares:

```yaml
# Profiles: activar/desactivar servicios según el entorno
services:
  app:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    profiles: [prod, staging, dev]

  adminer:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    profiles: [dev]  # Solo en desarrollo

  backup:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    profiles: [prod]  # Solo en producción

# depends_on con condiciones
  worker:
    build: .
    depends_on:
      redis:
        condition: service_started
      db:
        condition: service_healthy
      migrations:
        condition: service_completed_successfully

# healthcheck: monitoreo de estado
  db:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s
```

```bash
# Activar por perfil
docker compose --profile prod up -d
docker compose --profile dev up -d

# Condiciones
docker compose up -d --wait  # Espera a que todos estén healthy
```

### YAML anchors vs extends

`extends` está deprecado. Usa anclas YAML para reutilizar configuraciones:

```yaml
# Moderno: YAML anchors
x-app-defaults: &app-defaults
  restart: unless-stopped
  logging:
    driver: json-file
    options:
      max-size: "10m"

services:
  web:
    <<: *app-defaults
    build: .

  worker:
    <<: *app-defaults
    build: ./worker
```

### Docker Bake (HCL)

Para builds complejos, Docker Bake usa archivos HCL:

```hcl
# docker-bake.hcl
variable "TAG" {
  default = "latest"
}

group "default" {
  targets = ["app", "worker"]
}

target "app" {
  context = "./app"
  dockerfile = "Dockerfile"
  tags = ["ghcr.io/mi-org/app:${TAG}"]
  cache-from = ["type=gha"]
  cache-to = ["type=gha,mode=max"]
  platforms = ["linux/amd64", "linux/arm64"]
}
```

```bash
# Build con Bake
docker buildx bake
docker buildx bake app
docker buildx bake --set app.tags=mi-app:v2
```

## Conceptos clave explicados a fondo

### Imágenes vs Contenedores

Una **imagen** es una plantilla inmutable de solo lectura que contiene el sistema de archivos y la configuración de la aplicación. Un **contenedor** es una instancia ejecutable de una imagen: una capa de lectura/escritura (capa de contenedor) se añade sobre las capas de solo lectura de la imagen.

```bash
# Una imagen puede crear múltiples contenedores
docker build -t mi-app:v1 .     # Crea la imagen
docker run -d --name c1 mi-app:v1
docker run -d --name c2 mi-app:v1  # Dos contenedores distintos, misma imagen
```

### Capas (Layer Caching)

Cada instrucción en el Dockerfile crea una capa. Docker cachea cada capa por su hash. Si una capa no ha cambiado, Docker reusa la cacheada.

```dockerfile
# ORDEN ÓPTIMO: de lo que menos cambia a lo que más cambia
FROM python:3.12-slim           # Capa 0 — cambia raramente
WORKDIR /app                    # Capa 1 — cambia raramente
COPY requirements.txt .         # Capa 2 — cambia con dependencias
RUN pip install -r requirements.txt  # Capa 3 — se reconstruye si cambia requirements.txt
COPY . .                        # Capa 4 — cambia en cada commit
CMD ["python", "main.py"]       # Capa 5 — metadatos
```

Si cambias `main.py` pero no `requirements.txt`, Docker reusa las capas 0–3 y solo reconstruye capa 4 en adelante. Esto hace que builds repetidos sean ~O(1) en el caso ideal.

Para maximizar el cache:
1. Ordena instrucciones de menos a más cambiantes
2. Usa `.dockerignore` para no mandar archivos que no necesitas
3. Separa dependencias del código (`COPY requirements.txt` antes de `COPY .`)
4. Usa `--cache-from` en CI para reusar imágenes previas como caché
5. Combina `RUN` comandos con `&&` para no crear capas extra
6. Ten cuidado con `COPY .`: si cualquier archivo en el contexto cambia, invalida la caché de esa capa

### COPY vs ADD

```dockerfile
COPY archivo.txt /destino/      # Copia archivos locales al contenedor
ADD archivo.tar.gz /destino/    # COPY + extracción automática de tarballs + URLs
```

**Regla: usa siempre `COPY`** a menos que necesites específicamente la extracción automática de `ADD`. `ADD` con URLs es considerado mala práctica porque las URLs deberían descargarse con `curl` dentro de `RUN` para mejor control de caché y limpieza.

### ENTRYPOINT vs CMD

Ambos definen el comando que se ejecuta al arrancar el contenedor. La diferencia está en cómo se combinan con los argumentos de `docker run`:

```dockerfile
# Formas de CMD:
CMD ["python", "app.py"]          # exec form (JSON array) — PREFERIDA
CMD python app.py                  # shell form — invoca /bin/sh -c
CMD ["python"]                     # solo el ejecutable, args por docker run

# Formas de ENTRYPOINT:
ENTRYPOINT ["python"]              # exec form — PREFERIDA
ENTRYPOINT python app.py           # shell form — no acepta args de docker run
```

**Comportamiento combinado:**

| Dockerfile | `docker run imagen` | `docker run imagen --help` |
|---|---|---|
| `CMD ["python", "app.py"]` | Ejecuta `python app.py` | Ejecuta `python app.py --help` (args sustituyen a CMD) |
| `ENTRYPOINT ["python"]` + `CMD ["app.py"]` | Ejecuta `python app.py` | Ejecuta `python --help` (args sustituyen a CMD, no a ENTRYPOINT) |
| `ENTRYPOINT ["python"]` (sin CMD) | Error — falta argumento | Ejecuta `python --help` |

**Patrón recomendado:** `ENTRYPOINT` para el ejecutable fijo y `CMD` para los argumentos por defecto. Así puedes sobreescribir args con `docker run imagen --version`.

### Dockerfile multi-stage

Permite usar múltiples imágenes base en un mismo Dockerfile. La etapa final solo contiene lo necesario para ejecutar la app, reduciendo drásticamente el tamaño.

```dockerfile
# ETAPA 1: build — imagen pesada con compiladores
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /bin/app .

# ETAPA 2: runtime — imagen mínima solo con el binario
FROM scratch
COPY --from=builder /bin/app /bin/app
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

```bash
docker build -t go-app .
docker images go-app  # ~10 MB en lugar de ~800 MB (golang:1.22 pesa ~800 MB)
```

Para Node.js:

```dockerfile
# ETAPA 1: build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ETAPA 2: runtime con solo assets compilados
FROM node:20-alpine
WORKDIR /app
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
COPY --from=builder --chown=appuser:appgroup /app/dist ./dist
COPY --from=builder --chown=appuser:appgroup /app/package*.json ./
RUN npm ci --omit=dev --ignore-scripts
USER appuser
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

Para Python:

```dockerfile
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
RUN adduser --disabled-password --no-create-home appuser
COPY --from=builder /root/.local /home/appuser/.local
COPY --chown=appuser:appuser . .
ENV PATH=/home/appuser/.local/bin:$PATH
USER appuser
CMD ["python", "main.py"]
```

### ARG vs ENV

```dockerfile
# ARG: solo disponible durante el build
ARG VERSION=latest
RUN echo "Construyendo versión $VERSION"

# ENV: disponible en build y en runtime
ENV NODE_ENV=production
ENV DATABASE_URL=postgres://localhost:5432/db

# ARG con valor por defecto desde --build-arg
ARG BUILD_NUMBER
RUN echo "Build #$BUILD_NUMBER" > /build.txt
```

```bash
docker build --build-arg VERSION=1.2.3 -t mi-app .
```

- **ARG**: se pasa con `--build-arg` en `docker build`. No persiste en la imagen final (a menos que se use `ENV`). Útil para versiones, tokens de build, mirrors.
- **ENV**: persiste en el contenedor en runtime. Útil para configuración de la app.
- **Seguridad**: nunca pongas secrets en `ENV` — la imagen los expone. Usa `--secret` de BuildKit o mounts de secrets en runtime.

### EXPOSE

`EXPOSE` es puramente documentación: no abre ningún puerto. Solo indica qué puertos espera la aplicación:

```dockerfile
EXPOSE 8080  # Documenta que la app escucha en 8080
```

Para realmente abrir puertos, usa `-p` en `docker run` o `ports:` en compose:

```bash
docker run -p 8080:8080 mi-app   # Abre 8080 en host → 8080 en contenedor
```

### HEALTHCHECK

Permite que Docker monitoree la salud del contenedor:

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
```

Estados: `starting` → `healthy` → `unhealthy`. Swarm y K8s usan esto para reiniciar contenedores o redirigir tráfico. En compose:

```yaml
services:
  app:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

### Volúmenes: bind mount, volume, tmpfs

Tres formas de montar datos en contenedores:

```bash
# 1. VOLUMEN (gestionado por Docker, persistente)
docker volume create mis-datos
docker run -v mis-datos:/data ubuntu

# 2. BIND MOUNT (directorio del host, para desarrollo)
docker run -v /host/ruta:/container/ruta ubuntu
docker run --mount type=bind,src=/host/ruta,target=/container/ruta ubuntu

# 3. TMPFS (en memoria, no persiste, para datos efímeros)
docker run --tmpfs /app/temp ubuntu
```

| Tipo | Persistencia | Rendimiento | Caso de uso |
|---|---|---|---|
| Volume | Sí (en `/var/lib/docker/volumes`) | Excelente | BD, datos de producción |
| Bind mount | Sí (en el host) | Excelente | Desarrollo, hot reload |
| tmpfs | No (se pierde al parar) | Muy rápido (RAM) | Caché, sesiones, tmp |

En compose:

```yaml
services:
  app:
    volumes:
      - type: volume
        source: datos
        target: /data
      - type: bind
        source: ./src
        target: /app/src
      - type: tmpfs
        target: /tmp

volumes:
  datos:
```

### Redes: bridge, host, overlay, macvlan

```bash
# Bridge (por defecto): contenedores en el mismo host se comunican por IP
docker network create --driver bridge mi-red
docker run --network mi-red --name web nginx
docker run --network mi-red --name api node  # api puede resolver "web" por DNS

# Host: el contenedor usa la pila de red del host (sin aislamiento)
docker run --network host nginx  # Accesible en localhost:80 directamente

# Overlay: multi-host, para Swarm
docker network create --driver overlay --attachable mi-red-overlay

# Macvlan: asigna IP real de la LAN al contenedor
docker network create --driver macvlan --subnet=192.168.1.0/24 --gateway=192.168.1.1 -o parent=eth0 macvlan-red
```

En compose:

```yaml
services:
  web:
    networks:
      - frontend
  api:
    networks:
      - frontend
      - backend
  db:
    networks:
      - backend

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # Sin acceso externo
```

### Seguridad

**1. No ejecutar como root**

```dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
```

En Alpine:
```dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
```

En Debian/Ubuntu:
```dockerfile
RUN groupadd -r appgroup && useradd -r -g appgroup appuser
USER appuser
```

**2. Secrets: nunca en imágenes**

```bash
# BuildKit: pasa secretos en build sin que queden en la imagen
docker build --secret id=mysecret,src=./secret.txt -t mi-app .
```

```dockerfile
# Dockerfile
RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret
```

En runtime, usa monturas de secrets (Docker Swarm) o archivos externos:

```yaml
services:
  app:
    secrets:
      - api_key
    environment:
      - API_KEY_FILE=/run/secrets/api_key

secrets:
  api_key:
    file: ./secrets/api_key.txt
```

**3. Capabilities: `--cap-drop`**

Por defecto, Docker da un conjunto restringido de capabilities Linux al contenedor. Reduce aún más:

```bash
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE mi-app
```

En compose:
```yaml
services:
  app:
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE
```

**4. Seccomp y AppArmor**

Docker aplica un perfil seccomp por defecto que bloquea ~44 syscalls peligrosas. Puedes personalizarlo:

```bash
docker run --security-opt seccomp=./custom-seccomp.json mi-app
docker run --security-opt apparmor=my-custom-profile mi-app
```

Para máximo aislamiento (pero menos compatible):

```yaml
services:
  app:
    security_opt:
      - no-new-privileges:true
      - seccomp=./seccomp.json
    read_only: true
    tmpfs:
      - /tmp
```

## Sistema de archivos

Docker tiene su propio sistema de archivos en capas (overlay2) que permite compartir datos entre el host y los contenedores, entre contenedores, y gestionar el almacenamiento eficientemente.

### Tipos de monturas

| Tipo | Persistencia | Rendimiento | Uso principal |
|---|---|---|---|
| **Named volume** | Sí (gestionado por Docker) | Excelente | Datos de producción (BD, uploads) |
| **Bind mount** | Sí (ruta del host) | Excelente | Desarrollo, hot reload |
| **tmpfs** | No (en RAM) | Muy rápido | Caché, sesiones, datos temporales |

```bash
# Named volume (Docker gestiona la ruta)
docker volume create mis-datos
docker run -v mis-datos:/data ubuntu
docker volume inspect mis-datos  # Ruta real en /var/lib/docker/volumes/

# Bind mount (ruta explícita del host)
docker run -v /ruta/host:/ruta/contenedor ubuntu
docker run --mount type=bind,source=/ruta/host,target=/ruta/contenedor ubuntu

# tmpfs (solo en RAM)
docker run --tmpfs /app/temp:noexec,nosuid,size=64M ubuntu
```

### docker cp: copiar archivos

```bash
# Del host al contenedor
docker cp ./archivo.conf contenedor:/etc/app/config.conf

# Del contenedor al host
docker cp contenedor:/var/log/app.log ./app.log

# Copiar directorios completos
docker cp ./data/ contenedor:/app/data/
docker cp contenedor:/app/backup/ ./backup/
```

### COPY vs ADD en Dockerfile

```dockerfile
# COPY: solo copia archivos locales al contenedor
COPY archivo.txt /destino/
COPY --chown=appuser:appgroup . /app

# ADD: COPY + extracción automática de tarballs + URLs
ADD archivo.tar.gz /destino/   # Extrae automáticamente
ADD https://ejemplo.com/file /destino/  # Descarga (mala práctica)
```

**Regla:** usa siempre `COPY`. `ADD` con URLs es mala práctica (mejor `curl` en `RUN`). `ADD` con tarballs es aceptable pero prefiere `COPY` + `RUN tar -xf`.

### Contexto de build y .dockerignore

El **contexto** es todo lo que envías al daemon de Docker para construir. El `.dockerignore` excluye archivos:

```dockerignore
node_modules
.git
.env
*.md
.gitignore
Dockerfile
.dockerignore
dist
.cache
*.log
```

```bash
# Ver el tamaño del contexto antes de build
docker build -t mi-app .  # Muestra 'Sending build context...'

# Solo enviar lo necesario
docker build -f ./app/Dockerfile ./app  # Contexto = ./app
```

### docker import/export (contenedores a tarballs)

```bash
# Exportar contenedor a tarball (incluye capa de escritura)
docker export mi-contenedor > mi-contenedor.tar
docker export mi-contenedor | gzip > mi-contenedor.tar.gz

# Importar tarball como imagen
cat mi-contenedor.tar | docker import - mi-imagen:importada
docker import http://ejemplo.com/imagen.tar.gz mi-imagen:importada
```

### docker save/load (imágenes a tarballs)

```bash
# Guardar imagen como tarball (preserva capas y metadatos)
docker save mi-app:latest > mi-app.tar
docker save mi-app:latest | gzip > mi-app.tar.gz

# Cargar imagen desde tarball
docker load < mi-app.tar
docker load -i mi-app.tar.gz

# Transferir imágenes sin registry
docker save mi-app:latest | ssh servidor docker load
```

| Comando | Origen | Destino | Preserva capas | Caso de uso |
|---|---|---|---|---|
| `export` | Contenedor | Tarball | No (una sola capa) | Snapshots, debugging |
| `import` | Tarball | Imagen | No | Crear imagen desde export |
| `save` | Imagen | Tarball | Sí | Transferir imágenes, backups |
| `load` | Tarball | Imagen | Sí | Restaurar imágenes desde save |

### docker diff: cambios en el contenedor

```bash
# Muestra archivos añadidos, modificados y eliminados en la capa de escritura
docker diff mi-contenedor

# Formato: A (añadido), C (modificado), D (eliminado)
# A /app/logs/access.log
# C /app/config.json
# D /app/temp/cache.tmp
```

Útil para debugging: ver qué archivos modificó un proceso dentro del contenedor.

### Overlay2: el sistema de archivos en capas

Docker usa el driver **overlay2** (Linux nativo) para unir capas en un sistema de archivos único:

```text
Capa superior (contenedor, r/w)
---
Capa N (última instrucción Dockerfile, r/o)
---
Capa 3 (RUN pip install, r/o)
---
Capa 2 (COPY requirements.txt, r/o)
---
Capa 1 (WORKDIR, r/o)
---
Capa 0 (FROM python:3.12-slim, r/o)
```

- **Copy-on-Write (CoW)**: si un contenedor modifica un archivo de una capa inferior, overlay2 lo copia a la capa superior (r/w) antes de modificarlo
- **Compartición**: si dos contenedores usan la misma imagen base, comparten las mismas capas en disco
- **Eficiencia**: las capas comunes se descargan una sola vez, aunque las usen varias imágenes

```bash
# Ver capas de una imagen
docker history mi-app:latest
docker inspect mi-app:latest --format '{{.RootFS.Layers}}'

# Ver uso de disco por capas
docker system df
```

### Build cache

Docker cachea cada capa por el hash de su instrucción y archivos. La caché se invalida cuando:

1. Cambia el contenido de un archivo `COPY` o `ADD`
2. Cambia el comando de un `RUN`
3. Cambia la imagen base (`FROM`)
4. Una capa anterior se invalida (cascada)

```bash
# Forzar reconstrucción sin caché
docker build --no-cache -t mi-app .

# Usar imagen previa como fuente de caché (útil en CI)
docker build --cache-from ghcr.io/mi-org/app:latest -t mi-app .

# Ver qué capas se usaron de caché
docker build --progress=plain -t mi-app . 2>&1 | grep CACHED
```

Fuente: [Docker storage drivers](https://docs.docker.com/storage/storagedriver/), [Overlay2 driver](https://docs.docker.com/storage/storagedriver/overlayfs-driver/), [docker cp reference](https://docs.docker.com/engine/reference/commandline/cp/), [docker save/load](https://docs.docker.com/engine/reference/commandline/save/), [Build cache](https://docs.docker.com/build/cache/)

## Algoritmos

Docker no es un lenguaje de programación y no tiene algoritmos en el sentido tradicional. Sin embargo, sus mecanismos internos tienen comportamientos que se pueden analizar en términos de complejidad y eficiencia.

### Capas: union filesystem (O(n) para resolución)

Cada capa es una diferencia respecto a la anterior. Cuando el contenedor lee un archivo, overlay2 debe recorrer las capas de arriba abajo hasta encontrarlo:

```text
Lectura de /etc/passwd -> busca en capa r/w -> no está -> capa N -> no está -> ... -> capa 0 (imagen base) -> lo encuentra
```

En el peor caso, la resolución es **O(n)** donde n = número de capas. En la práctica, el caché de metadatos del kernel (dcache) hace que las lecturas repetidas sean O(1). Por eso se recomienda tener ~20-50 capas como máximo, no cientos.

### Cache invalidation (O(n) en capas modificadas)

Cuando una capa cambia, todas las capas siguientes deben reconstruirse:

```text
FROM python:3.12-slim    # Capa 0 — cacheada
WORKDIR /app             # Capa 1 — cacheada
COPY requirements.txt .  # Capa 2 — ¡CAMBIA!
RUN pip install -r ...   # Capa 3 — se reconstruye (depende de 2)
COPY . .                 # Capa 4 — se reconstruye (depende de 3)
CMD ["python", "app.py"] # Capa 5 — metadatos, no se reconstruye
```

Si la capa 2 se invalida, las capas 3 y 4 también. La complejidad es **O(n)** donde n = capas desde el cambio hasta el final. Por eso el orden óptimo es de menos a más cambiante: minimiza el número de capas afectadas.

### Dependencias entre servicios (resolución topológica)

`depends_on` en compose crea un grafo de dependencias. Docker Compose lo resuelve con un orden topológico:

```yaml
services:
  web:
    depends_on: [api, redis]
  api:
    depends_on:
      db:
        condition: service_healthy
  worker:
    depends_on: [redis, db]
  redis:
  db:
```

Grafo: web -> api -> db, web -> redis, worker -> redis, worker -> db
Orden topológico: redis, db -> api, worker -> web

La resolución es **O(V + E)** (V = servicios, E = dependencias). No se permiten dependencias cíclicas — error de validación.

### Scheduling en Swarm/Kubernetes

Swarm usa un algoritmo de **spreading**: distribuye réplicas entre nodos para minimizar el desbalance. K8s usa un scheduler más complejo con:

- **Predicados** (filtros): el nodo debe cumplir requisitos (CPU, memoria, taints)
- **Prioridades** (puntuación): elige el mejor nodo según peso (recursos libres, afinidad)

```text
Nodo A: 70% CPU usado, 60% RAM usado -> score: 30
Nodo B: 30% CPU usado, 40% RAM usado -> score: 60 (menos cargado)
```

Complejidad: **O(P x N)** donde P = número de pods a asignar y N = número de nodos.

### Round-robin en docker-compose --scale

```bash
docker compose up -d --scale api=5
```

Compose crea 5 réplicas del servicio `api`. Docker DNS resuelve el nombre del servicio con **round-robin**:

```text
api -> 172.17.0.2 (primera petición)
api -> 172.17.0.3 (segunda)
api -> 172.17.0.4 (tercera)
...
api -> 172.17.0.2 (vuelta a empezar)
```

Comportamiento: **O(1)** por resolución DNS. No hay estado compartido, el balanceo es estadísticamente uniforme.

### Health check polling

Docker ejecuta healthchecks periódicamente según el intervalo configurado:

```text
t=0  -> healthcheck ejecutado -> healthy
t=30 -> healthcheck ejecutado -> healthy
t=60 -> healthcheck ejecutado -> unhealthy (timeout)
t=90 -> healthcheck ejecutado -> unhealthy (3er intento)
t=90 -> contenedor marcado como unhealthy -> reinicio
```

Comportamiento: **O(1)** por healthcheck. El overhead es el del comando en sí (normalmente un curl o pg_isready).

### Tabla resumen

| Concepto | Complejidad / Comportamiento | Factor determinante |
|---|---|---|
| Resolución de capas (overlay2) | O(n) peor caso, O(1) con caché | n = número de capas |
| Cache invalidation | O(n) capas desde el cambio | Orden del Dockerfile |
| Dependencias (compose) | O(V + E) topológico | V = servicios, E = depends |
| Scheduling Swarm | Spreading (balance de recursos) | Nodos y réplicas |
| Scheduling K8s | O(P x N) predicados + prioridades | Pods y nodos |
| Round-robin DNS | O(1) por resolución | Número de réplicas |
| Health check | O(1) por intervalo | Intervalo configurado |
| Build context transfer | O(tamaño contexto) | Archivos enviados al daemon |

## Patrones de diseño en Docker

### Sidecar Container

Un contenedor auxiliar que acompaña al principal en el mismo pod/task y extiende o gestiona su funcionalidad.

**Proxy sidecar** (inyectar un reverse proxy junto a la app):

```yaml
services:
  app:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    networks:
      - backend

  sidecar-proxy:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    ports:
      - "80:80"
    networks:
      - backend
      - frontend

networks:
  frontend:
  backend:
    internal: true
```

La app solo escucha en la red interna `backend`, el sidecar proxy recibe tráfico externo y lo reenvía.

**Logging sidecar** (colectar logs y enviarlos a un agregador externo):

```yaml
services:
  app:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - logs:/var/log/app

  log-collector:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - logs:/logs:ro
    configs:
      - source: fluentbit-conf
        target: /fluent-bit/etc/fluent-bit.conf
    depends_on:
      - app

configs:
  fluentbit-conf:
    file: ./fluent-bit.conf

volumes:
  logs:
```

### Ambassador Container

Un proxy que abstrae la conexión a un servicio externo. El contenedor app se conecta a `localhost` del ambassador, y el ambassador enruta al servicio real.

```yaml
services:
  app:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    environment:
      - DATABASE_URL=postgres://user:pass@ambassador:5432/db
    depends_on:
      - ambassador

  ambassador:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - ./haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro
    environment:
      - DB_HOST=db-produccion.externo.com
      - DB_PORT=5432
    # Ambos contenedores comparten la misma red
```

La app nunca conoce la ubicación real de la BD. Cambias el backend en el ambassador sin tocar la app.

### Init Containers

Contenedores que se ejecutan antes que el principal para preparar el entorno (migraciones, seed de datos, permisos, etc.).

```yaml
services:
  init-db:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/miapp
    depends_on:
      db:
        condition: service_healthy
    profiles:
      - setup  # No se ejecuta en producción normal

  app:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    depends_on:
      db:
        condition: service_healthy
    # En producción, las migraciones se ejecutan como parte del CI/CD
```

En Kubernetes este patrón es nativo con `initContainers:`. En Docker Compose se simula con `depends_on` + profiles, o con scripts de entrypoint que verifican estado.

### Blue/Green Deploy con etiquetas

Estrategia de despliegue sin downtime: dos versiones (blue = actual, green = nueva) coexisten, y se cambia el tráfico atómicamente.

```yaml
services:
  app-blue:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    ports:
      - "3001:3000"
    networks:
      - app-net
    profiles:
      - blue

  app-green:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    ports:
      - "3002:3000"
    networks:
      - app-net
    profiles:
      - green

  nginx:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    ports:
      - "80:80"
    depends_on:
      - app-blue
      - app-green
```

El nginx balancea entre `app-blue:3000` y `app-green:3000`. Para cambiar, editas el upstream en nginx.conf y recargas:

```bash
docker compose --profile blue up -d   # Despliegas blue
# Verificas que blue funciona
docker compose --profile green up -d  # Despliegas green al lado
# Cambias nginx.conf para apuntar a green
docker compose exec nginx nginx -s reload
docker compose --profile blue down    # Apagas blue
```

## Composición, herencia y polimorfismo

Docker no es POO, pero sus mecanismos se entienden mejor con analogías de objetos:

### Composición (docker-compose)

Así como en POO un objeto contiene otros objetos, `docker-compose` compone servicios, redes y volúmenes en una aplicación completa:

```yaml
# docker-compose como "clase compuesta"
services:
  web:        # Un "objeto" que contiene...
    build: .  # ...su propia lógica
  db:         # Otro "objeto"
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
  cache:      # Otro "objeto"
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
```

Cada servicio es autocontenido e intercambiable. Cambias `postgres` por `mysql` sin tocar `web`. Es **composición sobre herencia**: prefieres tener servicios pequeños y reemplazables que imágenes enormes que heredan de todo.

### Herencia (FROM)

`FROM` es el equivalente a la herencia en imágenes:

```dockerfile
# "Clase base"
FROM python:3.12-slim AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt

# "Subclase" que hereda de base y añade comportamiento
FROM base AS development
COPY . .
CMD ["python", "dev_server.py"]

# Otra "subclase"
FROM base AS production
COPY . .
RUN pip install gunicorn
CMD ["gunicorn", "app:app", "-b", "0.0.0.0:8000"]
```

Así como en Python `class Production(Base):`, aquí `FROM base AS production` hereda todo de `base` y añade o sobreescribe. El MRO aquí es lineal: cada capa hereda de la anterior.

### Polimorfismo (un compose, múltiples entornos)

El mismo `compose.yml` se comporta distinto según el perfil:

```yaml
services:
  app:
    build: .
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/miapp
    profiles:
      - dev
      - staging
      - prod

  db-dev:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    ports:
      - "5432:5432"
    profiles:
      - dev

  db-prod:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    environment:
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_password
    secrets:
      - db_password
    profiles:
      - prod
```

```bash
docker compose --profile dev up    # Contenedor dev: app + db-dev
docker compose --profile prod up   # Contenedor prod: app + db-prod (con secrets)
```

Misma interfaz (`compose.yml`), comportamientos distintos según el contexto. Eso es polimorfismo.

## Concurrencia y escalado

Docker ofrece múltiples formas de escalar aplicaciones, desde un solo host hasta clústeres multi-nodo.

### docker compose --scale

Escala servicios horizontalmente en un solo host:

```bash
docker compose up -d --scale api=5 --scale worker=3
```

La red interna de Docker balancea entre las réplicas usando DNS round-robin. Limitación: todas las réplicas corren en el mismo host y comparten recursos.

```yaml
services:
  api:
    build: .
    ports:
      - "3000"  # Sin mapeo fijo — Docker asigna puertos efímeros
    environment:
      - REDIS_URL=redis://redis:6379

  redis:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
```

Con `ports: "3000"` (sin host:container), Docker asigna un puerto aleatorio del host para cada réplica:

```bash
docker compose up -d --scale api=3
docker compose ps api  # Muestra 3 contenedores con puertos distintos
```

### Docker Swarm services --replicas

Swarm escala a través de múltiples nodos:

```bash
# Inicializar clúster
docker swarm init
docker swarm join --token SWMTKN-1-... 192.168.1.10:2377  # En workers

# Crear servicio con réplicas
docker service create \
  --name api \
  --replicas 5 \
  --publish published=80,target=3000 \
  --network overlay-net \
  --limit-cpu 0.5 \
  --limit-memory 256M \
  mi-app:latest

# Escalar
docker service scale api=10

# Actualizar rolling update
docker service update \
  --image mi-app:v2 \
  --update-parallelism 2 \
  --update-delay 10s \
  api
```

El balanceador de carga integrado de Swarm (Ingress) distribuye tráfico entre todas las réplicas, incluso en diferentes nodos.

### Kubernetes HPA (Horizontal Pod Autoscaler)

Kubernetes escala pods basado en métricas (CPU, memoria, métricas personalizadas):

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
```

```bash
kubectl autoscale deployment api --cpu-percent=70 --min=2 --max=20
```

### Comparativa de escalado

| Herramienta | Ámbito | Escalado | Balanceo | Persistencia | Instalación |
|---|---|---|---|---|---|
| Compose --scale | Un host | Manual | DNS RR | Volúmenes locales | Incluido en Docker |
| Swarm | Multi-host declarativo | Manual/automático | Ingress LB | Volúmenes + NFS/Gluster | Incluido en Docker |
| Kubernetes | Multi-host completo | HPA automático | Service + Ingress | PVC + CSI | Minikube / Managed |
| Nomad | Multi-host | Job scaling | Consul + Fabio | CSI | HashiCorp stack |

Fuente: [Docker Compose scale](https://docs.docker.com/compose/how-tos/scale/), [Docker Swarm service create](https://docs.docker.com/engine/reference/commandline/service_create/), [Kubernetes HPA](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/)

## Escala de aprendizaje: de 0 a 100

Cada nivel incluye lo que debes saber y un proyecto para fijar los conceptos.

### Nivel 0–15: Fundamentos absolutos

**Qué aprender:**
- Qué es un contenedor: proceso aislado con su propio sistema de archivos
- `docker run`, `docker ps`, `docker stop`, `docker rm`
- `docker pull`, `docker images`, `docker rmi`
- Diferencia entre imagen (plantilla) y contenedor (instancia)
- `docker run hello-world` y entender qué pasa
- `docker run -it ubuntu bash` — explorar un contenedor interactivo
- `docker run -d nginx` — contenedor en background
- Conceptos clave: los contenedores comparten el kernel del host. Un contenedor corriendo es un proceso más en el host (pstree / ps aux | grep docker). Los contenedores NO son máquinas virtuales — arrancan en milisegundos y no tienen SO propio.

**Proyecto:** *Servidor web estático* — crea un contenedor nginx que sirva un `index.html` con "Hola Mundo Docker". Usa `docker run -d -p 8080:80 -v $(pwd):/usr/share/nginx/html nginx:alpine`. Accede en `http://localhost:8080`. Reflexión: ¿cuánto ocupa la imagen nginx:alpine? ¿Por qué es tan pequeña?

### Nivel 15–30: Dockerfile y builds

**Qué aprender:**
- Dockerfile básico: `FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`
- Orden de instrucciones y layer caching
- `.dockerignore` — qué excluir y por qué
- `docker build -t nombre .` y entender el contexto de build
- `EXPOSE`, `ENV`, `ARG`
- Diferencia entre `RUN`, `CMD` y `ENTRYPOINT`
- `COPY` vs `ADD` (siempre COPY)
- Conceptos clave: cada instrucción crea una capa. Las capas se cachean por hash. Si ordenas bien (de menos a más cambiante), los builds incremental son ~O(1). El contexto de build es todo lo que envías al daemon — `.dockerignore` reduce el contexto.

**Proyecto:** *App Node.js dockerizada* — crea un Dockerfile para una app Express que responda en `GET /`. Implementa layer caching: copia `package.json` primero, instala, luego copia el resto. Añade `.dockerignore`. Cambia el código fuente y observa que solo la última capa se reconstruye. Mide tiempos con y sin caché.

### Nivel 30–45: Docker Compose y multi-servicio

**Qué aprender:**
- `compose.yml`: `services`, `build`, `image`, `ports`, `volumes`, `environment`
- `docker compose up`, `down`, `logs`, `exec`, `ps`
- Dependencias entre servicios con `depends_on`
- Variables de entorno y archivos `.env`
- Redes en compose: bridge por defecto, redes personalizadas
- Profiles: entornos dev/staging/prod con el mismo compose
- Conceptos clave: compose es composición de servicios. Cada servicio es un contenedor independiente pero se comunican por red interna. `depends_on` controla orden de arranque. Profiles seleccionan qué servicios se ejecutan.

**Proyecto:** *App web + BD + caché* — compose con un servicio web (Node.js/Python), PostgreSQL y Redis. La web consulta la BD y cachea en Redis. Usa `depends_on` con `condition: service_healthy`. Variables de entorno para credenciales. Profile "dev" expone puertos de BD, profile "prod" no.

### Nivel 40–55: Procesamiento multimedia con Docker

**Qué aprender:**
- Contenedores FFmpeg (`jrottenberg/ffmpeg`): conversión, compresión, extracción de audio, captura de frames
- ImageMagick en contenedor para procesamiento por lotes de imágenes
- OpenCV para visión artificial dockerizada
- Streaming: Jellyfin, Plex, Nginx con módulo RTMP
- GStreamer para pipelines de medios
- GPU passthrough con `--gpus all` y nvidia-container-runtime
- WebRTC: mediasoup y Janus Gateway en contenedores
- docker-compose para pipelines multimedia completos

**Conceptos clave:** los contenedores multimedia evitan instalar dependencias nativas — FFmpeg 6.0 tiene ~1528 codecs y cada versión puede cambiar flags. En contenedor tienes la versión exacta. La GPU se pasa con `--gpus all` (requiere nvidia-container-toolkit). Para streaming en vivo, Nginx RTMP es la opción más ligera; Jellyfin da una interfaz completa.

**Proyecto:** *Pipeline de video* — docker-compose con FFmpeg para transcodificar vídeos, ImageMagick para miniaturas, y Jellyfin para servirlos. Bind mounts para input/output. Opcional: acelera con GPU.

### Nivel 45–60: Multi-stage, volúmenes y redes

**Qué aprender:**
- Multi-stage builds: `FROM ... AS builder`, `COPY --from=builder`
- Volúmenes: bind mount (desarrollo), volume (producción), tmpfs (caché efímero)
- Redes avanzadas: bridge, host, overlay, macvlan
- `docker network create`, conectar contenedores a múltiples redes
- `docker volume create`, inspect, backup
- `HEALTHCHECK` para monitorear estado del contenedor
- logging drivers: `json-file` (por defecto), `local`, `syslog`, `fluentd`
- Conceptos clave: multi-stage separa build de runtime — la imagen final solo tiene lo necesario para ejecutar. Bind mounts son para desarrollo (editas en host, se refleja en contenedor). Volúmenes son para datos que deben persistir. tmpfs para datos temporales que no necesitan persistencia.

**Proyecto:** *App Go con multi-stage* — app Go que sirve una API REST. Dockerfile multi-stage: compila en `golang:1.22`, runtime en `scratch` (~10 MB final). Bind mount para desarrollo, volume para logs. Healthcheck en `/health`. Red separada para BD y otra para frontend.

### Nivel 60–75: Seguridad, registros y CI/CD

**Qué aprender:**
- No ejecutar como root: `USER appuser`, `addgroup`/`adduser`
- `--cap-drop=ALL --cap-add=NET_BIND_SERVICE`
- Secrets: `--secret` en build, monturas de secrets en runtime
- `.dockerignore` para no filtrar credenciales
- `docker scout` (o Trivy) para escanear vulnerabilidades
- Docker Hub, GHCR, Harbor: login, tag, push, pull
- Tags semánticos: `v1.2.3`, SHA, `latest`
- GitHub Actions: build + push con cache
- Conceptos clave: los contenedores ejecutan como root por defecto — cambia a usuario no root. Las capabilities de Linux se pueden reducir al mínimo. Los secrets nunca deben estar en la imagen. El escaneo de vulnerabilidades es parte del pipeline.

**Proyecto:** *CI/CD pipeline* — repositorio con GitHub Action que: (1) construye la imagen Docker con multi-stage, (2) escanea con `docker scout`, (3) etiqueta con SHA del commit + versión semántica, (4) publica en GHCR. La imagen ejecuta como usuario no root. Los secrets de BD se pasan en runtime, no en build.

### Nivel 75–90: Swarm y orquestación básica

**Qué aprender:**
- `docker swarm init`, `docker swarm join`, `docker node ls`
- `docker service create`, `service ls`, `service ps`, `service scale`
- `docker stack deploy -c compose.yml` — despliega compose en Swarm
- Redes overlay para multi-host
- Secrets y configs en Swarm
- Rolling updates: `--update-parallelism`, `--update-delay`
- `docker stack services`, `docker stack ps`
- Conceptos clave: Swarm convierte un grupo de servidores en un clúster lógico. Los servicios con `--replicas` se distribuyen entre nodos. Las redes overlay conectan contenedores en diferentes hosts. El balanceador de carga integrado distribuye tráfico.

**Proyecto:** *Cluster Swarm local* — inicia 3 nodos con `docker swarm init` + `docker swarm join` (usa máquinas virtuales con multipass o VMs locales). Despliega un stack con `docker stack deploy`: app web con 3 réplicas, BD con 1, Redis con 2. Haz rolling update de la web. Escala a 10 réplicas. Verifica que el balanceo distribuye tráfico.

### Nivel 90–100: Kubernetes, service mesh y producción

**Qué aprender:**
- Minikube: `minikube start`, `kubectl get nodes`, `kubectl get pods`
- Deployments, Services, ConfigMaps, Secrets, PVCs
- `kubectl apply -f deployment.yaml`, `kubectl expose`, `kubectl scale`
- Ingress controller para tráfico externo
- HPA (Horizontal Pod Autoscaler) con métricas de CPU
- Service Mesh: Istio o Linkerd para mTLS, tracing, canary deployments
- Observabilidad: Prometheus + Grafana, Loki para logs, Jaeger para tracing
- GitOps: ArgoCD o Flux para despliegues declarativos
- Conceptos clave: K8s es el estándar de la industria para orquestación. Minikube te da un clúster local de un nodo. Service Mesh añade mTLS, trazabilidad y control de tráfico. GitOps asegura que el estado real del clúster coincida con el repositorio Git.

**Proyecto:** *Microservicios en K8s* — tres microservicios (api, auth, frontend) desplegados en Minikube. Deployments con HPA, Services tipo ClusterIP, Ingress para tráfico externo. ConfigMaps para configuración, Secrets para credenciales. Prometheus recolecta métricas, Grafana las visualiza. Service Mesh Istio para mTLS entre servicios. GitOps con ArgoCD sincronizado desde un repo Git.

Fuente: [Docker Swarm docs](https://docs.docker.com/engine/swarm/), [Kubernetes docs](https://kubernetes.io/docs/), [Minikube docs](https://minikube.sigs.k8s.io/docs/), [Istio docs](https://istio.io/latest/docs/)

### Web scraper distribuido con cola (nivel 75)

```python
# scraper/worker.py
import os
import json
import redis
import requests
from bs4 import BeautifulSoup

REDIS_URL = os.environ.get('REDIS_URL', 'redis://redis:6379')
r = redis.Redis.from_url(REDIS_URL)

def scrape(url):
    resp = requests.get(url, timeout=10)
    soup = BeautifulSoup(resp.text, 'html.parser')
    titles = [h.get_text(strip=True) for h in soup.select('h2 a, h3 a')]
    return {'url': url, 'titles': titles, 'count': len(titles)}

def worker():
    while True:
        _, url = r.blpop('scrape:queue', timeout=0)
        print(f"Scraping {url.decode()}")
        result = scrape(url.decode())
        r.rpush('scrape:results', json.dumps(result))

if __name__ == '__main__':
    worker()
```

## Hacks y tips de productividad

**1. `docker system prune --volumes` — limpia todo lo no usado**

```bash
docker system prune -af --volumes
```

Elimina contenedores parados, redes no usadas, imágenes colgantes (`<none>:<none>`) y **volúmenes no referenciados**. Cuidado: los volúmenes contienen datos — asegúrate de que no los necesitas. Para limpieza más selectiva:

```bash
docker container prune     # Solo contenedores parados
docker image prune -a      # Solo imágenes no usadas
docker volume prune         # Solo volúmenes no referenciados
docker network prune        # Solo redes no usadas
```

**2. `dive` — inspecciona el contenido de cada capa**

```bash
# Instalación
docker pull wagoodman/dive
docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock wagoodman/dive mi-app:latest

# También como binario: https://github.com/wagoodman/dive
dive mi-app:latest
```

Muestra: árbol de capas, qué archivos añadió/modificó/eliminó cada capa, espacio ocupado por archivos duplicados, y eficiencia del Dockerfile (porcentaje de archivos inútiles en la imagen final).

**3. `lazydocker` — TUI interactiva para gestionar Docker**

```bash
# Instalación
docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock lazyteam/lazydocker

# O como binario
brew install lazydocker  # macOS
lazydocker
```

Interfaz en terminal con teclas rápidas: logs en vivo, inspección de contenedores, restart, exec en contenedor, todo sin escribir comandos largos.

**4. `docker scout` — análisis de vulnerabilidades integrado**

```bash
# Docker Desktop lo incluye. En Linux:
docker scout quickview mi-app
docker scout cves mi-app       # Lista CVEs detallados
docker scout recommendations mi-app  # Recomendaciones de imagen base
docker scout compare mi-app:v1 mi-app:v2  # Compara vulnerabilidades entre versiones
```

Alternativas open-source: `trivy image mi-app` (Aqua Security), `grype mi-app` (Anchore).

**5. `--progress=plain` — logs detallados del build**

```bash
docker build --progress=plain --no-cache -t mi-app .
```

Muestra cada paso del build con tiempos exactos, incluyendo la salida de comandos `RUN`. Útil para depurar Dockerfile en CI donde no ves la salida interactiva.

**6. BuildKit — builds paralelos y secretos**

BuildKit está activado por defecto desde Docker 23.0. Funcionalidades clave:

```dockerfile
# Sintaxis para activar BuildKit explícitamente
# syntax=docker/dockerfile:1

FROM python:3.12-slim

# Montar caché de pip entre builds (persiste en host)
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# Pasar secreto en build (no queda en la imagen)
RUN --mount=type=secret,id=api_key \
    echo "API key: $(cat /run/secrets/api_key)"
```

```bash
docker build --secret id=api_key,src=./api_key.txt -t mi-app .
```

BuildKit también paraleliza etapas independientes en multi-stage y cachea monturas.

**9. Docker socket proxy para seguridad**

Nunca montes `/var/run/docker.sock` directamente en un contenedor a menos que sea estrictamente necesario. Un proxy con permisos restringidos es más seguro:

```yaml
services:
  traefik:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - docker-socket-proxy:/var/run/docker.sock:ro

  docker-socket-proxy:
    image: "img/guia_0_100_docker/guia_0_100_docker_cover-1200.webp"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      CONTAINERS: 1  # Solo permite leer contenedores
      SERVICES: 1
      NETWORKS: 1
      TASKS: 1

volumes:
  docker-socket-proxy:
```
