Llevo meses construyendo un ecosistema de automatización que ejecuta pipelines de vídeo, scrapers de noticias y ahora **un generador de ideas de proyectos** — todo auto-hospedado con Docker y sin que yo tenga que mover un dedo. Lo que empezó como un grabador de directos de Twitch se ha convertido en una suite de 7+ herramientas interconectadas que funcionan 24/7.

**Mi motivación:** Quería automatizar lo repetitivo: grabar directos, comprimirlos, subirlos a Telegram, descargar de YouTube, scrapear noticias de cine... y ahora también que me salgan ideas de proyectos para programar sin tener que pensarlas yo. Todo ejecutándose solo.

---

## El problema real

Cada herramienta existente resolvía un trozo:
- **TwitchRecorder** grababa pero no comprimía ni subía
- **ffmpeg** convertía pero no monitorizaba
- **yt-dlp** descargaba de YouTube pero no subía a Telegram
- **Scrapers** scrapeaban pero no enviaban resultados
- **Ideas de proyectos** → yo mismo pensando, buscando, filtrando...

Necesitaba **conectar todo** en pipelines automáticos. Y que las ideas de proyectos me llegaran solas, sin buscarlas.

## Pipeline 1: Sendo (directo → compresión → Telegram)

El pipeline Sendo es la cadena de tres daemons que graba un directo, lo comprime y lo publica en Telegram. No hay una cola central, ni un broker, ni una base de datos: el contrato entre servicios es **el nombre del archivo y la carpeta donde aparece**. Cada servicio vigila la salida del anterior y hace su parte.

> Para el uploader como herramienta independiente (CLI, credenciales cifradas, clonado, vigilante) consulta [Telegram Ultimate Toolbox](/myprojects/telegram-ultimate-toolbox). Para todos los modos de conversión de FFmpeg, consulta [FFmpeg + yt-dlp](/myprojects/ffmpeg-yt-dlp). Aquí se explica la **integración del pipeline**, no cada herramienta por separado.

### Esquema de flujo

```

        /srv/devjobs-data/grabaciones/test/*_completed.mp4

        /srv/devjobs-data/comprimidos/*_compressed.mp4
                                    │

                 ┌─────────────────────────────────────┐

                                    │

                                       sus restos y la grabación original
```

Ramas de error previstas por el diseño:

```
proceso de grabación muere
   ├─ el directo sigue o cambia de plataforma → nueva parte __parteN
   ├─ la misma plataforma se reconecta       → nueva parte __parteN
   └─ no vuelve en 120 s                     → stop + concatenar partes

MP4 truncado (sin moov)   → ffmpeg -c copy lo repara antes de seguir
MP4 ilegible o < 60 s     → se mueve a grabaciones/test/.corruptos
subida incompleta         → no se marca como enviado y se reintenta
```

### El contrato entre servicios

Las rutas reales se montan con `DEVJOBS_DATA` (por defecto `/srv/devjobs-data`):

| Ruta en el host | Ruta en el contenedor | Quién la usa | Contenido |
|-----------------|----------------------|--------------|-----------|
| `grabaciones/AAAA/MM/` | `/recordings/AAAA/MM/` | Grabador | Grabación original, con fecha y keyword |
| `grabaciones/test/` | `/recordings/test/` y `/watch` | Grabador → monitor | Cola de `*_completed.mp4` |
| `comprimidos/` | `/comprimidos` | Monitor → uploader | `*_compressed.mp4` listos para subir |
| `partes/` | `/app/partes` | Uploader | Trozos temporales de vídeos > 2 GB |
| `grabaciones/test/.corruptos/` | `/watch/.corruptos` | Monitor | Vídeos que no pasan la validación |

El nombre del archivo es la información que viaja:

```
<canal>_<AAAA-MM-DD_HH-MM-SS>[_KW_<keyword>].mp4
```

Al terminar, el grabador crea un **enlace duro** `*_completed.mp4` en `test/` (si el sistema de archivos no lo permite, copia). Así el monitor ve el archivo completo sin mover ni duplicar la grabación original. El monitor escribe primero `*_compressed.mp4.tmp` y solo al terminar lo renombra: el uploader nunca puede coger un archivo a medio escribir.

### 1. Grabador: `twitchrecorder-sendo`

#### Código y ciclo de vida

- `main.py` carga la configuración, crea las carpetas y arranca `run_scheduler()`.
- `utils/config.py` rellena los valores que falten con `DEFAULT_CONFIG` y permite sobrescribir `record_path`, `test_path` y `copy_to_test` por variables de entorno.
- `utils/scheduler.py` comprueba la hora, espera hasta el primer `schedule` del día, crea un `Recorder` por canal, recarga `config.json` en cada vuelta para incorporar canales nuevos (los cambios en un canal ya cargado requieren recrear) y detecta colisiones de horario entre canales distintos.
- `utils/recorder.py` contiene la lógica pesada: elegir fuente, extraer título, grabar, reparar, cerrar partes y concatenar.

El scheduler no graba en paralelo todos los canales: mantiene un `Recorder` por canal y un hilo `monitor()` por grabación activa. Si un canal no está programado para hoy, se ignora. Si dos canales coinciden a la misma hora, avisa de la colisión y los graba igualmente en paralelo.

#### Detección de directo

Cada plataforma tiene su módulo:

| Plataforma | Detección | Grabación |
|------------|-----------|-----------|
| `twitch` | `streamlink.streams()` | `streamlink` con calidad `best` |
| `youtube` | `yt-dlp` contra `/@canal/live` | `yt-dlp -f best` |
| `kick` | API pública `kick.com/api/v2/channels/<canal>` | `yt-dlp -f best` |
| `web` | HLS propio + `yt-dlp` como respaldo | `yt-dlp` sobre la URL `.m3u8` |

La fuente `web` no se fía del HTML de una SPA. Hace una comprobación rápida del servidor, pide `/api/playback-domain` y construye la URL HLS. Después analiza el `m3u8` para detectar tres casos: playlist terminada (`#EXT-X-ENDLIST`), segmento demasiado antiguo o cola de segmentos congelada. Si no puede decidir, cae a `yt-dlp`. Cuando la web está activa, deja un diagnóstico de formatos en el log (`web_probe`).

`yt-dlp` recibe `--js-runtimes deno --remote-components ejs:github` porque YouTube exige un runtime de JavaScript para extraer formatos. Deno se instala en la imagen del grabador y se añade al `PATH`.

#### Keyword y nombre del archivo

`get_live_keyword()` obtiene el título real y lo normaliza:

1. Pasa todo a minúsculas.
2. Sustituye signos por espacios.
3. Elimina palabras vacías (`de`, `la`, `el`, `en`, `con`, `y`...).
4. Une las dos primeras palabras informativas con `_`.

Ejemplos: `Detective Conan Ep 123` → `detective_conan`; `One Piece 1090` → `one_piece`.

Casos especiales:

- **Web wrapper**: el título se pide **solo a la API de Kick** (`session_title`). Si falla, la keyword cae al nombre del canal. No se usa el HTML del wrapper porque devuelve un título genérico.
- **Twitch/YouTube/Kick directo**: se usa `yt-dlp`. Si el título es genérico (`canal (live)`), se usa la descripción como título real.
- **Sin título**: `_normalize_keyword(nombre_del_canal)` como último recurso.

La keyword viaja en el nombre (`_KW_<keyword>`) y es lo que usarán el monitor y el uploader para enrutar.

#### Resiliencia: cortes, reconexiones y cambio de plataforma

- La grabación se para con `SIGINT`, luego `SIGTERM` y solo al final `SIGKILL`. Así `yt-dlp`/`streamlink` pueden cerrar el MP4 y escribir el `moov`.
- Si el proceso muere antes de 30 s, se aplica un backoff progresivo (5, 10, 15, 20 s). Al quinto fallo rápido seguido, se cierra la grabación.
- Si el MP4 queda truncado, se repara con `ffmpeg -c copy` antes de concatenar o moverlo a la cola.
- Si el directo cambia de plataforma a mitad (por ejemplo web → Kick), se cierra la parte actual, se crea `__parte2` con la **misma keyword original** y se sigue grabando. Al final se concatenan todas las partes.
- La concatenación intenta primero `concat` con `-c copy` (rápido y sin pérdida). Si los códecs o resoluciones no coinciden, hace un reencode completo.
- Si la concatenación falla, se conservan las partes por separado para no perder contenido.


| Campo | Qué hace |
|-------|----------|
| `enabled` | Si es `false`, el canal se salta por completo |
| `platform` | Lista ordenada de fuentes; el orden es la prioridad |
| `url` | URL de la fuente `web` |
| `kick_channel` | Canal usado para pedir el título a la API de Kick desde la web |
| `detectar` | Activa la detección de episodios en el monitor |
| `corte` | Permite recortar intro/outro si hay detección |

| `record_path` | Carpeta donde se guardan las grabaciones originales |

Cada plataforma puede tener su propio `schedule`. Si una plataforma no tiene regla para hoy, no se usa. Si el canal tiene un `schedule` a nivel de canal, ese tiene prioridad; si todas las plataformas lo dejan vacío, el scheduler puede caer en el horario legacy (`days`/`start_time`). Los nombres de los días se comparan siempre en inglés (`Monday`, `Tuesday`...), independientemente del idioma del sistema.

#### Docker del grabador

`TwitchRecorder/Dockerfile` parte de `python:3.12-slim`, instala `ffmpeg`, `curl`, `unzip`, deno y las dependencias de `requirements.txt`. Fija el usuario `1000:1000` (el compose lo repite) para que los archivos creados en el volumen pertenezcan al UID 1000 del host.

`TwitchRecorder/docker-compose.yml` monta:

- `config.json` en modo solo lectura.
- `entrypoint.sh` en modo solo lectura.
- `${DEVJOBS_DATA:-/srv/devjobs-data}/grabaciones` en `/recordings`.
- Define `TZ` y `restart: unless-stopped`.

`entrypoint.sh` imprime la zona horaria y la fecha antes de lanzar `python -u main.py`. Es una ayuda de diagnóstico: Telegram y los `schedule` dependen de que la hora sea correcta.

### 2. Compresor: `ffmpeg_monitor-sendo`

#### Bucle de vigilancia

`ffmpeg-yt-dlp/scripts/monitor_folder.sh` es el corazón del segundo paso:

1. Crea `WATCH_DIR` y `OUTPUT_DIR` si no existen.
2. Procesa primero lo que ya estuviera pendiente.
3. Entra en un bucle cada `POLL_INTERVAL` segundos.
4. Con `COMPLETED_ONLY=true`, solo mira archivos `*_completed.(mp4|mkv|avi|mov|webm|flv|ts|m4v|mpg|mpeg)`.
5. Antes de comprimir, valida con `ffprobe` que el archivo es legible y dura al menos `MIN_DURACION` (60 s por defecto). Si no, lo mueve a `.corruptos`.

#### Configuración por canal

No existe `monitor.json`. El monitor lee la misma `TwitchRecorder/config.json` mediante `get_monitor_config.py`. El helper:

1. Extrae el canal del nombre del archivo.
2. Busca ese canal en `config.json`.
3. Toma la primera plataforma que tenga definidos `detectar`, `corte` o `descripcion`.

Devuelve un JSON con esos tres flags. Si no encuentra el canal, usa `detectar: true` y `corte: true`. El flag `descripcion` permite saltarse OCR y corte; no transporta una descripción al uploader, que en ese caso usa el nombre del canal como caption.

#### Compresión

El comando base es:

```bash
ffmpeg -i entrada \
  -c:v libx264 -crf 28 -preset fast -threads 4 \
  -c:a aac -b:a 128k \
  -map 0:v:0 -map 0:a:0 \
  -map_metadata 0 -movflags +faststart \
  -f mp4 salida.tmp
```

> **Sobre el 720p:** el compose actual no define `RESOLUTION`, así que el monitor conserva la resolución original del directo. Para forzar 720p, añade `RESOLUTION=720` a las variables del servicio `monitor`; el script aplica entonces `scale` + `pad` antes de codificar.

Detalles importantes:

- Se mapea explícitamente el primer vídeo y el primer audio. Así se descartan subtítulos y pistas extra que impiden la reproducción en línea de Telegram.
- `+faststart` mueve el `moov` al principio para que Telegram pueda reproducir mientras descarga.
- Si el resultado supera `TAMANO_MAX_MB` (1900 MB por defecto), se recalcula el bitrate de vídeo y se hacen **dos pasadas** apuntando a ese tamaño. La primera pasada no escribe audio; la segunda genera el MP4 final.
- Se escribe en `.tmp` y se renombra al terminar.
- Al terminar se borra el archivo de `test/` (el enlace duro), no la grabación original. La original sigue en `grabaciones/AAAA/MM/` hasta que el uploader confirma la subida.

La detección de episodios del monitor es opcional. Si `detectar` es `true`, llama a `detectar_episodios.py` y puede recortar extremos si `corte` también es `true`. En la práctica, la metadata de episodios que usa el uploader se calcula en el propio uploader cuando no hay un JSON previo: el monitor no escribe un sidecar de episodios en el código actual.

#### Docker del monitor

`ffmpeg-yt-dlp/Dockerfile.monitor` usa Alpine e instala `ffmpeg`, `bash`, `findutils`, `su-exec`, `python3`, `tesseract-ocr`, `tesseract-ocr-data-eng`, `gallery-dl` y `yt-dlp`. Crea el usuario `monitor` con UID 1000.

El compose lo ejecuta como `root` y lanza el script con `su-exec 1000`: arranca como root para poder usar `su-exec`, pero el script corre como UID 1000, el mismo usuario que crea los archivos. Monta los scripts en solo lectura, `TwitchRecorder/config.json` en solo lectura, `grabaciones/test` en `/watch` y `comprimidos` en `/comprimidos`.

Variables principales del monitor (las que no están en el compose usan el default del script):

| Variable | Valor de ejemplo | Efecto |
|----------|------------------|--------|
| `WATCH_DIR` | `/watch` | Carpeta de entrada |
| `OUTPUT_DIR` | `/comprimidos` | Carpeta de salida |
| `POLL_INTERVAL` | `30` | Segundos entre pasadas |
| `COMPLETED_ONLY` | `true` | Solo procesa `*_completed.*` |
| `CRF` | `28` | Calidad de compresión |
| `PRESET` | `fast` | Velocidad de libx264 |
| `THREADS` | `4` | Hilos de ffmpeg |
| `TAMANO_MAX_MB` | `1900` | Umbral para las dos pasadas |
| `MIN_DURACION` | `60` | Duración mínima válida |
| `MONITOR_CONFIG_FILE` | `/app/TwitchRecorder/config.json` | Config de canales |

### 3. Uploader: `telegram-uploader-sendo`

#### Credenciales y sesión

El uploader **no usa `BOT_TOKEN`**. Sube como una cuenta de Telegram mediante Telethon y necesita:

| Archivo | Contenido |
|---------|-----------|
| `config/config.bin` | `api_id` y `api_hash` cifrados con Fernet |
| `config/secret.key` | Clave que descifra `config.bin` |
| `sessions/uploader.session` | Sesión de usuario ya autenticada |

`cargar_credenciales()` descifra `config.bin`; si no existe, permite `UPLOADER_API_ID` y `UPLOADER_API_HASH` por entorno. `pipe_setup.sh` crea o renueva `uploader.session` con login interactivo (teléfono, código y 2FA si aplica).

#### Bucle de subida

`run_autoupload()` vigila cada `UPLOADER_INTERVALO` segundos (60 por defecto) todos los `*_compressed.*` de las carpetas configuradas. Para cada archivo:

1. Extrae la keyword de `_KW_<keyword>` y elimina los sufijos `_compressed`, `_completed` y `__parteN`.
2. Extrae el canal del primer token del nombre.
3. Busca destinos:
   - En `grupos`, por coincidencia flexible con la keyword; si no hay, usa `default`.
   - En `foros`, por prioridad: canal → keyword → episodios → primer foro con su tema `general`.
4. Si hay foros y no hay metadata de episodios, ejecuta OCR con `tesseract`.
5. Genera el caption: rango de episodios sin la palabra “Episodio” (`1-4`, `Temporada 2 · 1-4`) o `Directo de <canal>` si no hay rango.
6. Si el archivo supera 2 GB, lo divide en trozos de 90 minutos con `ffmpeg -c copy` y `+faststart`.
7. Genera un thumbnail y los atributos de vídeo con `ffprobe` (duración, ancho, alto, `supports_streaming`) para que Telegram lo reproduzca en línea.
8. Sube a cada destino con `send_file`, usando `reply_to` con el `topic_id` cuando es un foro.
9. Solo si todas las partes se subieron a todos los destinos, marca el archivo como enviado y lo borra.

El registro de enviados es **en memoria**. La fuente de verdad es el propio archivo: si la subida no se completa, el comprimido sigue en disco y se reintenta en la siguiente pasada. Al completar, `limpiar_restos()` borra el comprimido, sus logs, el sidecar de episodios si existiera y las partes temporales. Después `borrar_grabacion_original()` elimina la grabación original de `grabaciones/`, salvo que `UPLOADER_BORRAR_ORIGINAL=0`.

#### Ruteo a foros y temas

Un foro de Telegram es un grupo con temas. Cada tema tiene un `topic_id` (el id del mensaje raíz). En `config/grupos.json` se declara el foro, su tema general y la lista de temas:

```json
{
  "default": -1000000000000,
  "grupos": [
    { "nombre": "serie_demo", "id": -1000000000001 }
  ],
  "foros": [
    {
      "id": -1000000000002,
      "nombre": "foro_demo",
      "general": 101,
      "temas": [
        { "nombre": "serie_a", "id": 102 },
        { "nombre": "serie_b", "id": 103 },
        { "nombre": "peliculas", "id": 104 }
      ]
    }
  ]
}
```

- `default`: grupo de respaldo si ninguna keyword coincide.
- `grupos`: chats sueltos sin temas.
- `foros`: grupos con foro. `general` es el tema al que van los vídeos que no coinciden con ninguno.
- `temas`: nombre visible y `topic_id`.

La comparación normaliza mayúsculas, tildes y signos; además tolera singular/plural y pequeñas variaciones (`serie` ↔ `series`, `cry` ↔ `cryyy`). Por eso conviene que los nombres de los temas sean reconocibles en el título del directo.

#### OCR y caption

Si no hay `<nombre>_episodios.json` junto al comprimido, el uploader hace su propio OCR:

- Extrae un frame cada `UPLOADER_OCR_STEP` segundos (90 por defecto).
- Recorta la franja superior (25 % de la altura) y la escala al doble.
- Convierte a grises, sube contraste, aplica sharpen y binariza.
- Ejecuta `tesseract` con los modos PSM 3, 6 y 7 y se queda con el texto que más patrones de episodio contiene.
- Reconoce `S01E02`, `1x02`, `Episodio 5`, `EP. 3`, `#12`, etc., además de errores típicos de OCR (`O` → `0`, `l` → `1`).
- Descarta detecciones aisladas que se solapan con la detección principal.
- Si detecta “película” en varios frames, genera `Película · TÍTULO`.

El caption final no repite la palabra “Episodio” cuando el texto ya es un rango: `Episodio 1-4` se muestra como `1-4`. Si no hay rango, se usa el nombre del canal.

#### Docker del uploader

`downloader_telegram/Dockerfile` parte de `python:3.12-slim` e instala `ffmpeg`, `tesseract-ocr` y `tesseract-ocr-spa`, además de Telethon, `cryptography`, `cryptg`, Pillow, `imagehash` y las dependencias del CLI. El compose monta `app`, `config`, `sessions`, `partes`, `comprimidos` y `grabaciones`, y define `UPLOADER_INTERVALO`, `UPLOADER_PARTES`, `UPLOADER_GRABACIONES` y `UPLOADER_BORRAR_ORIGINAL`. El resto se puede añadir al servicio:

| Variable | Valor de ejemplo | Efecto |
|----------|------------------|--------|
| `UPLOADER_INTERVALO` | `60` | Segundos entre pasadas |
| `UPLOADER_PARTES` | `/app/partes` | Carpeta de trozos > 2 GB |
| `UPLOADER_GRABACIONES` | `/grabaciones` | Originales que se borran tras subir |
| `UPLOADER_BORRAR_ORIGINAL` | `1` | `0` desactiva el borrado del original |
| `UPLOADER_OCR_STEP` | `90` | Paso del OCR en segundos |
| `UPLOADER_HEARTBEAT` | `60` | Frecuencia del log “Monitoreo: N pendientes” |

### Operación del pipeline

Los tres contenedores son daemons con `restart: unless-stopped`. Los scripts de `servicios/` encapsulan las operaciones habituales:

| Script / alias | Qué hace |
|----------------|----------|
| `pipe_up` | Levanta grabador, monitor y uploader |
| `pipe_ps` | Estado de los tres contenedores |
| `plogs` | Logs de los tres a la vez, con color por contenedor |
| `pipe_once` | Una sola pasada del uploader y sale |
| `pipe_verificar` | Comprueba `config.bin`, `grupos.json` y `uploader.session` sin subir nada |
| `pipe_credenciales.sh` | Crea `config.bin`, `secret.key` y `uploader.session` |
| `pipe_setup` | Solo login interactivo del uploader; `--reset` borra la sesión actual |
| `pipe_rebuild` | Rebuild + recreate de los tres (cambios de código) |
| `pipe_recreate` | Recreate sin rebuild (cambios de config) |
| `pipe_down` | Para el pipeline con `down` en los tres compose |
| `pipe_test` | Copia un vídeo de prueba a `comprimidos/` para probar el ruteo |
| `pipe_chats` | Lista chats/grupos desde la sesión del uploader |
| `pipe_topics` | Lista los temas de un foro |

`pipe_rebuild` es necesario cuando cambia código Python o un Dockerfile. `pipe_recreate` basta cuando solo cambia `config.json`, `grupos.json` o una variable de entorno.

El auto-arranque lo gestiona `twitch-stream-pipeline.service`. El servicio levanta los tres composes con `docker compose up -d` y los para con `down`. La instalación de ese servicio se explica en [la guía de instalación](/posts/instalacion-devjobs).

### Diagnóstico rápido

| Síntoma | Dónde mirar |
|---------|-------------|
| No detecta directo | `tw_logs`: fuente, `schedule`, hora y plataforma |
| La web está “live” pero no avanza | `web_probe` y el análisis de HLS congelado |
| YouTube no extrae formatos | deno en el contenedor y flags `--js-runtimes` |
| El monitor no coge el archivo | Nombre `*_completed.mp4` en `grabaciones/test` |
| El vídeo se mueve a `.corruptos` | `ffprobe` no lo lee o dura menos de 60 s |
| El uploader no sube | `pipe_verificar`, sesión, `grupos.json` y keyword |
| El vídeo aparece como documento | Atributos de vídeo/thumbnail y `supports_streaming` |
| Queda basura en `comprimidos/` | La subida no se completó; el archivo se reintenta |

## Pipeline 2: YouTube → Telegram (160 canales)

Pipeline diario que descarga vídeos de 160 canales de YouTube, los convierte a 720p y los sube a Telegram con temas por canal.

### Por qué 160 canales

Cada canal tiene contenido distinto: tutoriales, noticias, entrevistas. El pipeline baja lo nuevo de cada canal y lo organiza en un foro de Telegram con un tema por canal: `canal_demo_1` en su tema, `canal_demo_2` en otro, `canal_demo_3` en otro...

### Configuración (producción)

- **Canales: 160** en `channels.json` (6 habilitados por defecto)
- **Temas: 160** (uno por canal en el foro de ejemplo)
- **Calidad: 720p H.264/AAC** — balance calidad/tamaño (límite 50MB bot)
- **Cron: 01:00 → 18:00** — horario nocturno
- **Límite: 1 vídeo por canal** (`max_videos: 1`)

```
convert.py (convierte a 720p, 95% target size)
   ↓

   ↓
18:00 Cron para
```

## Sistema de Aliases: Control desde cualquier Terminal

Una sola instalación (`bash servicios/instalar_aliases.sh`) pone 40+ aliases en `~/.bashrc` que funcionan desde cualquier carpeta.

### Convención (clave para no perderse)

| Prefijo | Significado | Ejemplo |
|---------|-------------|---------|
| `pipe_*` | Los 3 daemons del pipeline a la vez | `pipe_up`, `pipe_down`, `plogs` |
| `*_logs` | Ver logs de un daemon | `ff_logs`, `tw_logs`, `tg_logs` |
| `*_stop` | Parar un daemon | `ff_stop`, `tw_stop`, `tg_stop` |
| `*_restart` | Reiniciar | `ff_restart`, `tw_restart` |
| `*_manual_*` | Versión para probar a mano | `ff_midu`, `tw_run` |
| `*_down` | Parar TODO el proyecto | `tg_down`, `tw_down` |
| `*_sys_*` | Control vía systemd | `pipe_sys_start`, `pipe_sys_stop` |

## Cron Pipeline: Automatización Diaria

Pipeline de YouTube con cron 01:00 → 18:00.

```bash
# Cron
0 1 * * * /home/usuario/devjobs/yt-to-telegram/scripts/run_pipeline_cron.sh
```

El script: marca timestamp, calcula hora parada, docker compose up, bucle cada 5 min (¿sigue corriendo? ¿es hora de parar?), 18:00 docker compose down, resumen.

```bash
# Ver logs de hoy
cat data/yt-pipeline/logs/cron_$(date +%Y%m%d).log

# Ejecutar manualmente
bash /home/usuario/devjobs/yt-to-telegram/scripts/run_pipeline_cron.sh

# Parar
cd yt-to-telegram && docker compose down
```

Si el cron se para antes (apagas PC), vídeos pendientes se guardan en `pending_videos.log` y la próxima vez continúa desde ahí.
