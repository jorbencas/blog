Llevo meses construyendo un ecosistema completo de automatización que ejecuta pipelines de vídeo, bots de IA, scrapers de noticias y herramientas de productividad — todo auto-hospedado con Docker y sin intervención manual. Lo que empezó como un grabador de directos de Twitch se convirtió en una suite de 6 herramientas interconectadas.

**Mi motivación:** Quería automatizar tareas repetitivas: grabar directos, comprimirlos, subirlos a Telegram, descargar vídeos de YouTube, generar contenido de programación con IA, y scrapear noticias de cine. Todo esto ejecutándose solo, 24/7, sin que yo tenga que hacer nada.

---

## El problema real

Cada herramienta existente resolvía un problema:
- **TwitchRecorder** grababa directos pero no los comprimía ni subía
- [**ffmpeg**](https://ffmpeg.org/) convertía vídeos pero no los monitorizaba
- [**yt-dlp**](https://github.com/yt-dlp/yt-dlp) descargaba de YouTube pero no subía a Telegram
- **Bots de Telegram** existían pero no tenían IA ni descargas
- **Scrapers** scrapeaban pero no enviaban resultados

Necesitaba **conectar todo** en pipelines automáticos.

## Pipeline 1: Twitch → Telegram (Sendo Sama)

Automatización completa que graba directos de **sendo sama**, los comprime a 720p y los sube a un grupo de Telegram con temas organizados por serie.

> **Detalle técnico completo:** [Telegram Ultimate Toolbox: Descargador Masivo, Clonador, Vigilante y Uploader con Docker](/myprojects/telegram-ultimate-toolbox)

### El grupo de Telegram y el sistema de temas

El grupo de Telegram **"Stream Tecnologia"** usa el sistema de **foro/temas** de Telegram. Cada tema es un hilo independiente dedicado a una serie o contenido específico. Cuando subo un vídeo de "One Piece", ese vídeo aparece en el tema de "One Piece" dentro del grupo, no en el chat general.

Esto es clave porque mantiene el grupo organizado: cada serie tiene su propio hilo, los usuarios pueden seguir solo las series que les interesan, y el contenido no se mezcla.

### Configuración por canal

Cada canal tiene su propia configuración de horarios, plataformas y comportamiento:

```json
{
    "channels": {
        "sendosama": {
            "platform": [
                { "platform": "web", "url": "https://watch.sendosama.net/", "detectar": false, "corte": false },
                { "platform": "youtube", "channel": "sendosenpai" },
                { "platform": "twitch", "detectar": false, "corte": false },
                { "platform": "kick", "detectar": false, "corte": false }
            ],
            "start_time": { "Sunday": "19:00", "*": "21:30" },
            "dias_plataforma": {
                "Sunday": ["youtube", "web", "kick", "twitch"],
                "*": ["web"]
            }
        },
        "midudev": {
            "platform": [
                { "platform": "youtube", "detectar": false, "corte": false },
                { "platform": "twitch", "detectar": false, "corte": false }
            ],
            "days": ["Monday"],
            "start_time": "18:00"
        },
        "mouredev": {
            "platform": [
                { "platform": "youtube", "detectar": false, "corte": false },
                { "platform": "twitch", "detectar": false, "corte": false }
            ],
            "days": ["Thursday"],
            "start_time": "18:00"
        }
    },
    "record_path": "/recordings",
    "check_every": 30,
    "max_duration": "24:00:00",
    "retry_interval": 1,
    "copy_to_test": true,
    "test_path": "/recordings/test"
}
```

**Características clave:**
- **`dias_plataforma`**: Cambia qué plataformas se prueban según el día (domingo YouTube primero, resto solo web)
- **`days`**: Días de la semana en los que se comprueba si hay directo (midudev lunes, mouredev jueves)
- **`start_time`**: Hora mínima para empezar a comprobar (str o dict por día)
- **`detectar`/`corte`**: Control de detección de episodios y corte de extremos por fuente (el config real los usa a `false` para no recortar)
- **`descripcion`**: Usar descripción del directo como caption (para YouTube)
- **Detección HLS sin navegador**: `is_live()` consulta el `m3u8` de la web directamente (API `/api/playback-domain`) en vez de yt-dlp, más rápido y fiable
- **Playlist congelada**: `_hls_estado()` detecta la web que sigue sirviendo el stream pero "congelada" (sin avance) y la marca como offline

### Flujo paso a paso

El pipeline de Twitch → Telegram son 6 pasos encadenados. **Cada paso vigila la carpeta donde el anterior deja su resultado** (patrón *watcher*): cuando un vídeo entra, lo procesa y lo deja listo para el siguiente. No hay una orquestación central que "llame" al paso siguiente — cada servicio se despierta solo al ver la carpeta llena.

```
 Twitch live
   │
   ▼
 ① twitchrecorder-sendo ──►  título → nombre  (keyword)
   │  data/pipeline/grabaciones/test/*_completed.mp4
   ▼
 ② ffmpeg_monitor-sendo ──►  720p, CRF 28, 2 pasadas si >1900MB
   │  data/out/*_720p.mp4
   ▼
 ③ OCR (ffmpeg_monitor-sendo) ──►  detecta serie por imagen del frame
   │
   ▼
 ④ telegram-uploader-sendo ──►  sube a temas de Telegram por keyword
   ▼
 Serie correcta (tema/foro)
```

1. **Grabar** — `twitchrecorder-sendo` graba el directo con calidad original (Twitch no guarda VODs indefinidamente).
2. **Keyword** — el mismo servicio extrae el título del directo y lo pone en el nombre, para poder ruteear a la serie correcta.
3. **Cola** — el vídeo espera en `data/pipeline/grabaciones/test/` como `*_completed.mp4` (patrón watcher: el siguiente servicio vigila esta carpeta).
4. **Comprimir** — `ffmpeg_monitor-sendo` convierte a 720p (CRF 28, 2 pasadas si >1900MB) porque Telegram tiene límite de 2GB y 720p es suficiente.
5. **OCR** — detecta episodios por imagen del frame: sabe qué serie es por la imagen (el frame del vídeo se parece a la serie, no al nombre).
6. **Subir** — `telegram-uploader-sendo` rutea por keyword a temas de Telegram: cada serie va a su tema/foro.

> **Salto de plataforma a mitad:** si el directo empieza en Twitch y el streamer se cambia a YouTube/web a mitad, **el pipeline no se rompe**. `twitchrecorder-sendo` vigila la playlist congelada: si el `m3u8` deja de avanzar, cierra la parte actual y abre `__parte2` esperando el nuevo enlace. Como la **keyword viene del título** (no de la plataforma), el `__parte2` conserva la misma serie y todo sigue ruteando al mismo tema de Telegram. Detalle completo en [13.4](#134-qué-pasa-si-el-directo-cambia-de-plataforma-a-mitad).

> **¿Qué tienes que montar tú?** Nada de Dockerfile a mano: el repo trae `docker-compose.yml` con los 3 servicios listos. Solo necesitas (1) `channels.json` con tus canales y (2) un grupo de Telegram con el sistema de *temas* activado. Lo demás — calendario, calidad, keywords — ya viene configurado. Detalle de cada servicio en [Contenedores Docker](#contenedores-docker).

> **Detalle técnico del compresor:** [FFmpeg + yt-dlp Pipeline: Conversor, Descargador y Editor de Vídeo con 33 Modos](/myprojects/ffmpeg-yt-dlp)

### Contenedores Docker

| Contenedor | Servicio | Función |
|------------|----------|---------|
| `twitchrecorder-sendo` | Grabador | Detecta directos, graba con calidad original, concatena partes |

### Detección de directo y playlist congelada (web)

La web de Sendo es una SPA de React sin `m3u8` en el HTML. Se obtiene el dominio del servidor HLS con la API interna `/api/playback-domain` y se construye la URL `ts:abr.m3u8`. `is_live()` comprueba ese `m3u8` directamente (mucho más barato que lanzar yt-dlp) y solo cae al extractor como seguridad cuando el estado es indeterminado.

El caso más tramposo es la **playlist congelada**: Sendo apaga el *visualizador* pero el servidor HLS sigue sirviendo un `m3u8` que ya no avanza. Con yt-dlp eso parecería un directo "para siempre". `_hls_estado()` (`utils/web.py`) lo resuelve con dos umbrales:

```python
_PDT_FUERA = 90   # el último segmento lleva >90s de antigüedad → fuera
_COLA_FUERA = 60  # la cola de segmentos no avanza durante 60s → fuera
```

- `#EXT-X-ENDLIST` o 404/410 → final limpio → fuera
- Último `#EXT-X-PROGRAM-DATE-TIME` con más de 90s → congelado → fuera
- Sin timestamps: se firma la cola (`#EXT-X-MEDIA-SEQUENCE` + último segmento) y si no cambia durante 60s → congelado → fuera

Así el pipeline no se queda grabando un stream fantasma: cuando la web se cae de verdad, detecta offline y puede cambiar de plataforma (Twitch/Kick) o parar. Al terminar, el log lo confirma:

```
17:35:28 [sendosama] Grabación finalizada (6.2 GB, 01:28:15)
```

### 13.1. La keyword que viaja: el contrato `_KW_` del nombre

El nombre del archivo es el **único canal de comunicación** entre grabador, monitor y uploader: no hablan entre sí por red, se pasan la información **dentro del propio nombre** del vídeo. Ese nombre sigue un contrato fijo:

```
sendosama_2026-08-13_20-15-00_KW_diario__parte1.mp4
```

| Trozo | Qué es | Quién lo pone | Por qué importa |
|-------|--------|---------------|-----------------|
| `sendosama` | @ del canal | TwitchRecorder | El uploader sabe qué config/tema usar |
| `2026-08-13_20-15-00` | Inicio del directo (fecha y hora) | TwitchRecorder | Ordena y deduplica |
| `_KW_` | Marcador de que empieza la **keyword** | TwitchRecorder | Es el punto de ruteo |
| `diario` | La **keyword** (del título del directo) | TwitchRecorder | El uploader la mapea a un tema de Telegram |
| `__parte1` | Número de parte (si hubo cortes) | TwitchRecorder + concat | Une todas las partes al final |

**Reglas del contrato que lo hacen todo posible:**

1. La keyword se genera **una sola vez**, al principio (cuando se detecta el directo), y **nunca cambia** durante todo el pipeline.
2. Cada cambio de nombre del archivo (parte, comprimido, subido) **hereda la misma keyword**: por eso el uploader sabe que `diario__parte3.mp4` y `diario_compressed.mp4` son **la misma serie**.
3. Todo el ruteo (a qué tema de Telegram va cada vídeo) se decide **solo** por la keyword.

### 13.2. La keyword y el OCR: `_descripcion.json` y el sidecar

De cada directo, además del vídeo, se guarda un **sidecar** `<nombre>_descripcion.json` — un archivo JSON que acompaña al mp4 con la info del directo. Tiene dos usos:

1. **Caption de Telegram**: si el directo lleva `descripcion: true`, el uploader usa esa descripción directamente como caption del mensaje (sin pasar por OCR).
2. **Detección de episodios**: si no hay sidecar (o no trae contenido), el monitor hace **OCR** sobre los frames para detectar episodios y cortar intros/outros.

Cuando el vídeo cambia de nombre (p. ej. de `_parte1` a `_compressed`), **el sidecar conserva el nombre base**, así que siempre se puede relacionar qué sidecar va con qué vídeo.

> 💡 **Detalle del corte:** si `corte: true` y el OCR detectó episodios, el monitor recorta los extremos con **CORTE_MARGEN=300** (5 min de margen por lado) para no cortar diálogo. Los episodios se detectan cada `OCR_STEP=180`s sobre la franja superior del frame.

### 13.3. IPC: cómo se hablan el monitor y el bot sin red

El monitor y el bot **no se comunican por red ni por base de datos**: usan **IPC por ficheros**. El monitor escribe JSON de **estado** en `comprimidos/.pipeline/` (que es el *único* montaje compartido en escritura):

| Fichero | Qué contiene | Quién lo lee |
|---------|--------------|--------------|
| `pipeline_status.json` | Estado actual del pipeline (grabando, comprimiendo, cuántos pendientes...) | El bot (para `/estado`) |
| `pipeline_logs.json` | Las últimas líneas de log | El bot (para `plogs`) |

El uploader también escribe su propio estado ahí. Así el bot **no necesita entrar al docker compose**: lee un fichero plano que el monitor ya ha escrito.

> ### ⚠️ No existe ningún `monitor.json`
>
> Error típico al buscar cómo configurar el monitor. El monitor `ffmpeg_monitor-sendo` **no se configura con un JSON**: sus parámetros van como **variables de entorno y flags** en su `docker-compose.yml`.

### 13.4. ¿Qué pasa si el directo cambia de plataforma a mitad?

El grabador no se entera (ni le importa) si el directo salta de YouTube a Kick a mitad de la emisión. Lo detecta así:

1. Mientras graba con yt-dlp, **comprueba el estado del proceso cada `check_every`**.
2. Si el proceso muere (plataforma X se cae), **espera** un margen antes de rendirse por si el streamer reaparece.
3. Si reaparece **en la misma plataforma** → **concatena y sigue** en el mismo archivo (sin duplicar nada).
4. Si reaparece en **otra plataforma** → cierra la parte actual y abre `__parteN`, marcando la nueva parte con **la misma keyword**.

Al final del directo, `concat` une todas las partes → el uploader ve **un único vídeo** con la serie correcta. Que el streamer saltara de plataforma **no cambia nada** para quien recibe el vídeo en Telegram.

> 🔗 El detalle completo de la **detección del directo** (playlist congelada, OCR, SPA sin m3u8) está en [el pipeline en myprojects](#detección-de-directo-y-playlist-congelada-web).

## Pipeline 2: YouTube → Telegram (160 canales)

Pipeline diario que descarga vídeos de 160 canales de YouTube, los convierte a 720p y los sube a un grupo de Telegram con temas organizados por canal.

### Por qué 160 canales

Cada canal de YouTube tiene contenido diferente: tutoriales, noticias, entrevistas, proyectos. En lugar de tener que revisar YouTube cada día, el pipeline descarga automáticamente los nuevos vídeos de cada canal y los organiza en el grupo de Telegram por canal/tema.

Por ejemplo:
- El canal de **Midudev** tiene su propio tema en el grupo
- El canal de **MoureDev** tiene otro tema
- El canal de **Carlos Azaustre** tiene otro

Cuando subo un vídeo de Midudev, ese vídeo aparece en el tema de "Midudev" dentro del grupo "Stream Tecnologia".

### Configuración

Estos son los parámetros reales del pipeline (los de producción, configurados para que **encajen en los límites de Telegram**):

- **Canales: 160** en `channels.json` (6 habilitados por defecto: Midudev, MoureDev, etc.) — los canales que sigo y quiero archivar.
- **Temas: 160** (uno por canal en "Stream Tecnologia") — organización por creador de contenido.
- **Calidad: 720p H.264/AAC** — balance entre calidad y tamaño (límite de 50MB de Telegram).
- **Cron: 01:00 → 18:00 (mismo día)** — horario nocturno para no saturar la red.
- **Límite: 1 vídeo por canal** (`"max_videos": 1`) — para no descargar todo el historial de cada canal.

### Flujo

```
01:00 Cron arranca
  ↓
download.py (descarga de 160 canales)
  ↓
convert.py (convierte a 720p, 95% target size)
  ↓
upload.py (sube a Telegram con topic_id)
  ↓
18:00 Cron para
```

```bash
# Ver logs del cron
cat data/yt-pipeline/logs/cron_$(date +%Y%m%d).log

# Parar manualmente
cd yt-to-telegram && docker compose down
```

## Bot de Telegram (@jorbencas_bot)

Bot interactivo con comandos, botones inline y contenido generado por IA. El bot se conecta al mismo grupo "Stream Tecnologia" para enviar contenido.

> **Detalle técnico completo:** [Telegram Ultimate Toolbox: Descargador Masivo, Clonador, Vigilante y Uploader con Docker](/myprojects/telegram-ultimate-toolbox)

### Comandos

- **`/descarga URL`** — Descarga vídeo de cualquier plataforma. `yt-dlp` baja, el bot convierte y envía como vídeo de Telegram.
- **`/tip`** — Tip de programación. Gemini + Wikipedia generan tips con preguntas de entrevista.
- **`/concepto`** — Concepto con código de ejemplo. Base de datos de 283 conceptos con interview questions.
- **`/tool`** — Herramienta IA. Herramientas seleccionadas de 2108 recursos migrados del blog.
- **`/noticias`** — Últimas noticias tech. Scrapers de 80+ fuentes españolas.

### Características técnicas

La descarga no es un simple `yt-dlp` (eso solo cubre la mitad de los sitios); el bot mezcla estrategias para que **cualquier link funcione**:

- **Descarga multicapa** — `yt-dlp` primero; si no soporta el sitio, **fallback HLS** para streams directos. Cubre lo que yt-dlp no sabe hacer.
- **Formato `bv+ba/b`** — baja por separado vídeo y audio y los **fusiona solo** (YouTube sirve streams separados). Sin este merge tendrías archivos mudo o sin vídeo.
- **Timeout 30 minutos** — los vídeos grandes tardan; 5 minutos era claramente insuficiente.
- **Conversión H.264/AAC 720p, 2 pasadas si >50MB** — H.264 es lo que Telegram espera; por encima de 50MB la Bot API no deja subir, así que se compressiona más.
- **IA Gemini** — genera tips, conceptos y noticias dinámicas sin repetir contenido (sin usar plantillas fijas).
- **Scrapers de 80+ fuentes españolas** — agrega noticias tech de medios españoles en un solo aviso.

## Sistema de Aliases: Control desde cualquier Terminal

El sistema de aliases es la capa de abstracción que hace que todo sea fácil de controlar. Un solo script instala más de 40 aliases en `~/.bashrc` que funcionan desde cualquier carpeta.

### Cómo se instala

```bash
# Una sola vez
bash servicios/instalar_aliases.sh && source ~/.bashrc
```

### Convención de nombres

Los aliases siguen un patrón claro para que nunca te pierdas:

| Prefijo | Significado | Ejemplo |
|---------|-------------|---------|
| `pipe_*` | Los 3 daemons del pipeline a la vez | `pipe_up`, `pipe_down`, `plogs` |
| `*_logs` | Ver logs de un daemon específico | `ff_logs`, `tw_logs`, `tg_logs` |
| `*_stop` | Parar un daemon específico | `ff_stop`, `tw_stop`, `tg_stop` |
| `*_restart` | Reiniciar un daemon | `ff_restart`, `tw_restart` |
| `*_manual_*` | Versión para probar a mano (con `--rm`) | `ff_midu`, `tw_run` |
| `*_down` | Parar TODO el proyecto (ambas instancias) | `tg_down`, `tw_down` |
| `tg_bot_*` | Bot API de Telegram | `tg_bot`, `tg_bot_logs` |
| `*_sys_*` | Control vía systemd | `pipe_sys_start`, `tg_bot_sys_status` |

### Ejemplos reales

```bash
# Pipeline completo de Twitch
pipe_up              # Arrancar los 3 daemons
plogs                # Ver logs de los 3 a la vez (color: azul/amarillo/rojo)
pipe_down            # Parar los 3
pipe_ps              # Estado de los 3 contenedores
pipe_recreate        # Recrear (aplica cambios de CONFIG)
pipe_rebuild         # Rebuild + recrear (cambios de CÓDIGO)

# Un proyecto individual
ff_logs              # Logs del monitor ffmpeg
ff_stop              # Parar el monitor
ff_restart           # Reiniciar el monitor
ff_midu              # Lanzar midu.sh interactivo (docker compose run --rm)

# Bot de Telegram
tg_bot               # Arrancar el bot
tg_bot_logs          # Ver logs
tg_bot_stop          # Parar
tg_bot_rebuild       # Rebuild imagen + arrancar
```

### Por qué no `docker compose up` directamente

Si ejecutas `docker compose down` en la carpeta de `downloader_telegram`, pararías **todos** los servicios de esa carpeta (uploader + bot + CLI). Los aliases evitan esto: `pipe_down` solo para los 3 daemons del pipeline, mientras que `tg_down` para todo el proyecto de Telegram.

## Systemd: Auto-arranque al Boot

Los servicios systemd hacen que el pipeline y el bot se levanten solos al encender el PC. No tienes que acordarte de nada.

### Servicios instalados

| Servicio | Qué hace | Por qué |
|----------|----------|---------|
| `twitch-stream-pipeline.service` | Arranca los 3 daemons del pipeline | Para que siempre esté grabando |
| `telegram-bot.service` | Arranca el bot API | Para que siempre esté respondiendo |

### Gestión

```bash
# Pipeline
sudo systemctl status   twitch-stream-pipeline.service   # ver estado
sudo systemctl restart  twitch-stream-pipeline.service   # reiniciar
sudo systemctl stop     twitch-stream-pipeline.service   # parar
sudo systemctl disable  twitch-stream-pipeline.service   # quitar auto-arranque

# Bot
sudo systemctl status   telegram-bot.service
sudo systemctl restart  telegram-bot.service

# O con aliases (sin sudo)
pipe_sys_start         # Arrancar pipeline
pipe_sys_stop          # Parar pipeline
pipe_sys_status        # Ver estado
tg_bot_sys_start       # Arrancar bot
tg_bot_sys_stop        # Parar bot
```

### Qué pasa al encender el PC

1. Systemd arranca `twitch-stream-pipeline.service`
2. El servicio ejecuta `docker compose up -d` en los 3 proyectos
3. Los 3 daemons empiezan a vigilar sus carpetas
4. Si hay un directo en curso, se empieza a grabar
5. Si hay vídeos en `grabaciones/test/`, se comprimen
6. Si hay vídeos en `comprimidos/`, se suben a Telegram

### Bootstrap automático en otra máquina

Un script hace todo el montaje en una máquina nueva (Windows + WSL2):

```bash
# Opción A (recomendada, sin descargar nada)
bash <(curl -fsSL https://raw.githubusercontent.com/jorbencas/devjobs/main/servicios/bootstrap_instalar.sh)

# Opción B
curl -fsSL -o bootstrap_instalar.sh https://raw.githubusercontent.com/jorbencas/devjobs/main/servicios/bootstrap_instalar.sh
chmod +x bootstrap_instalar.sh
./bootstrap_instalar.sh
```

El script hace 8 pasos:
1. Comprueba Docker y WSL2
2. Clona el repo en `~/devjobs`
3. Ajusta las rutas a tu máquina
4. Crea las carpetas de vídeo
5. Revisa secretos y credenciales
6. Construye las imágenes Docker
7. Instala el servicio systemd
8. Añade los aliases al `~/.bashrc`

## Cron Pipeline: Automatización Diaria

El pipeline de YouTube se ejecuta automáticamente cada día con un cron job:

### Configuración

```bash
# Cron: 01:00 arranca, 18:00 para (mismo día)
0 1 * * * /home/jorge/dev/devjobs/yt-to-telegram/scripts/run_pipeline_cron.sh
```

### Flujo interno del script

```
01:00 cron ejecuta el script
  ↓
1. Marca timestamp de inicio
  ↓
2. Calcula hora de parada (01:00 + 17h = 18:00)
  ↓
3. docker compose up -d yt-pipeline
  ↓
4. Bucle cada 5 minutos:
   - ¿Sigue corriendo el contenedor?
   - ¿Es hora de parar?
   - Log cada hora con tiempo restante
  ↓
5. 18:00: docker compose down
  ↓
6. Resume: vídeos convertidos sin subir
```

### Gestión manual

```bash
# Ver logs del cron de hoy
cat data/yt-pipeline/logs/cron_$(date +%Y%m%d).log

# Ejecutar manualmente ahora
bash /home/jorge/dev/devjobs/yt-to-telegram/scripts/run_pipeline_cron.sh

# Parar el pipeline
cd yt-to-telegram && docker compose down

# Ver si está corriendo
docker ps | grep yt-to-telegram
```

### Videos pendientes

Si el cron se para antes de tiempo (por ejemplo, si apagas el PC), los vídeos pendientes se guardan en `data/yt-pipeline/logs/pending_videos.log`. La próxima vez que arranque, el pipeline continuará desde donde se quedó.

### Conversión unificada

Todos los pipelines usan la misma configuración de ffmpeg:

```bash
ffmpeg -c:v libx264 -crf 28 -preset fast -vf scale=-2:720
       -c:a aac -b:a 128k -map 0:v:0 -map 0:a:0
       -map_metadata 0 -movflags +faststart -f mp4

# 2 pasadas si >50MB (bot Telegram) o >1900MB (monitor/uploader)
```

> 💡 ¿Quieres **archivar canales enteros de YouTube** sin subir a Telegram? El repo incluye `backup_youtube.sh`: descarga a `~/Backups/YouTube/<canal>/` con `--download-archive` (idempotente, solo baja lo nuevo) y metadatos incrustados. Toda su explicación está en la [guía de instalación](/posts/instalacion-devjobs#16-backup_youtubesh-respaldar-canales-de-youtube-enteros).

## Lo que aprendí

1. **Pipelines complejos**: Conectar 3 servicios que se comunican por archivos (watcher pattern) — cada uno vigila una carpeta y procesa lo que encuentra

3. **Bots de Telegram**: Comandos, botones inline, manejo de archivos grandes (>50MB con compresión automática)
4. **Scraping robusto**: Múltiples fuentes con fallbacks, deduplicación, y envío a Telegram

6. **IA en producción**: Gemini API para generación de contenido, fallback a bases de datos locales
7. **Sistemas de aliases**: Convención de nombres clara que hace que 40+ comandos sean fáciles de recordar
